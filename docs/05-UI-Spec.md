## 인증 화면 (`L-P0-03`에서 확정)

**문구 규칙 둘**
- **계정의 존재 여부를 흘리지 않는다.** 로그인 실패는 이메일이 틀렸는지 비밀번호가 틀렸는지 구분하지 않고, 재설정 메일 요청은 가입되지 않은 주소에도 같은 성공 문구를 낸다. 구분해 주면 주소만 넣어 보고 가입 여부를 알아낼 수 있다.
- **비밀번호 규칙을 우리가 다시 검증하지 않는다.** 길이·복잡도는 Supabase 설정이 정하고 화면은 그 결과를 전달만 한다. 두 곳에 두면 갈라진다.

| 화면 | h1 | 필드 (`name`) | 버튼·링크 |
|---|---|---|---|
| `/login` | 로그인 | `email`, `password` | **[로그인]** · [Google로 계속하기] · "비밀번호를 잊으셨나요?" · "계정이 없으신가요? 가입하기" |
| `/signup` | 회원가입 | `email`, `password` | **[가입하기]** · [Google로 계속하기] · "이미 계정이 있으신가요? 로그인" |
| `/signup?sent=1` | 메일을 확인해 주세요 | — | "로그인으로 돌아가기" |
| `/reset-password` | 비밀번호 재설정 | `email` | **[재설정 메일 보내기]** · "로그인으로 돌아가기" |
| `/reset-password?sent=1` | 메일을 확인해 주세요 | — | "로그인으로 돌아가기" |
| `/reset-password/update` | 새 비밀번호 설정 | `password` | **[비밀번호 저장]** |
| `/consent` | 시작하기 전에 | `privacy`, `age` (체크박스) | **[동의하고 시작하기]** · [동의하지 않음] · "개인정보처리방침 전문 보기" (HF-06) |
| `/privacy` | 개인정보처리방침 | — | — (로그인 없이 열리는 공개 페이지. 인증 카드보다 넓은 `max-w-2xl` 카드 한 장) |
| `/dashboard` | 대시보드 | — | [로그아웃] |
| `/auth/app/start` | 앱으로 돌아갈 수 없습니다 | — | — (허용되지 않은 `redirect_uri`일 때만 보인다. 정상이면 로그인 화면이나 앱으로 곧장 넘어간다 — `L-P0-04`) |

**비밀번호 칸에는 우리가 그린 [보기] 토글이 있다**(HF-02, 2026-09-25). 브라우저가 얹어 주는 기본 눈 버튼은 앱 웹뷰에서 **눌리지 않거나 아예 없어서**, 앱 안에서는 방금 친 글자를 확인할 길이 전혀 없었다. 버튼의 접근 이름은 상태에 따라 `비밀번호 보기` / `비밀번호 숨기기`이고 `aria-pressed`가 같은 사실을 한 번 더 말한다. 기본 눈 버튼은 `globals.css`가 숨긴다 — 남기면 브라우저에서 눈이 둘로 보인다. 세 화면(`/login`·`/signup`·`/reset-password/update`)이 같은 컴포넌트를 쓴다.

**`/consent` — 방침 동의 게이트**(HF-06, 2026-09-27). 동의 전 계정은 `(app)`의 어느 화면으로 가도 여기로 온다. 체크박스 라벨 `개인정보처리방침에 동의합니다` · `만 14세 이상입니다`가 접근 이름이다(`e2e/support/ui.ts`의 `acceptConsentThroughUi`가 이 글자에 기댄다). 둘 다 체크해야 하며 판정은 서버가 한다 — 빠지면 `?error=consent_required`(`개인정보처리방침 동의와 만 14세 이상 확인이 모두 필요합니다.`). [동의하지 않음]은 `quiet` 버튼이고 로그아웃이다(`/login?signedOut=1`). 이미 동의한 계정이 들어오면 `/dashboard`로 보낸다. "전문 보기"는 새 탭(`target="_blank"`)으로 연다 — 체크한 상태를 잃지 않게.

**인증 화면에는 대시보드로 가는 링크가 없다**(사용자 결정 2026-09-25). 앱 웹뷰는 세션이 없어 대시보드에서 이 화면으로 밀려온 것이라 그 링크는 누르면 제자리로 돌아온다 — 앱이 세 화면에서 그것을 숨기고 있었고, 웹에서 지워 덧칠할 것을 하나 줄였다.

**`?next=`** — `/login`·`/signup`은 로그인 뒤 돌아갈 내부 경로를 받아 폼·Google 버튼·서로의 링크에 그대로 싣는다. 앱 로그인(`AUTH-3`)이 이 길로 `/auth/app/start`에 돌아온다. 로그인 실패로 `?error=`가 붙어도 `next`는 남는다.

**가입은 메일 확인을 한 번 거친다**([`03-Architecture.md`](03-Architecture.md) §설계 결정 12). 제출 직후 대시보드로 가지 않고 안내 화면을 지난다.

안내 문구
- `/signup?sent=1` — `확인 메일을 보냈습니다. 메일의 링크를 눌러 가입을 완료해 주세요.`
- `/reset-password` — `가입한 이메일 주소로 재설정 링크를 보내 드립니다.`
- `/reset-password?sent=1` — `재설정 메일을 보냈습니다. 메일함을 확인해 주세요.`

**조판 (`L-DS-02`에서 확정)** — 주색 배경 가운데에 Tide 가로 락업(높이 24px)을 얹고, 그 아래 흰 카드 하나에 제목·안내·폼·보조 링크를 전부 담는다. 흰 카드와 주색 배경의 면 대비가 1.1:1뿐이라 **카드에는 언제나 테두리가 있다**(그림자를 쓰지 않는 대가다 — [`08-Design-System.md`](08-Design-System.md)).

- **카드 안의 인디고 채움 버튼은 하나다.** 주 행동([로그인]·[가입하기]·[재설정 메일 보내기]·[비밀번호 저장])만 채우고, [Google로 계속하기]는 흰 표면 + 테두리인 2차 버튼이다. 둘 다 채우면 어느 쪽이 기본 길인지가 사라진다.
- **안내 문구는 옅은 인디고 배너**(키트의 '확인 필요 배너' 면)이고 **아이콘을 달지 않는다.** 키트의 배너가 경고 아이콘을 다는 것은 행동을 요구하기 때문인데, 여기 문구는 알리기만 한다 — 경고 아이콘은 없는 긴급함을 만들고, 체크 아이콘은 성공이 아닌 문구("재설정 링크를 보내 드립니다")에 성공 표시를 붙인다.
- **오류는 빨간 배너 + 경고 아이콘.** 빨강이 쓰이는 두 자리 중 하나다(다른 하나는 마감).
- `/auth/app/start`의 오류 화면은 `(auth)` 그룹 밖이라 레이아웃을 물려받지 못한다. **같은 조판을 그 파일이 직접 한 번 더 그린다** — 사용자에게는 방금 지나온 로그인 화면과 이어지는 한 화면이어야 한다.

에러 문구는 `?error=<code>`로 전달한다. `code`는 Supabase `AuthError.code`를 그대로 쓰고, 문구 표는 `app/(auth)/messages.ts`가 SSOT다. 모르는 코드는 `문제가 생겼습니다. 잠시 후 다시 시도해 주세요.`로 합류시킨다.

## 대시보드 태스크 목록 (`L-P0-11`에서 확정, 보기는 `L-P1-10`)

**보기가 셋이다**(`DASH-9`) — 사이드바 주요 메뉴가 고르고, 한 화면에 **섹션 하나**가 선다. 비어 있어도 그린다. 제목 옆에 건수를 적는다.

| 보기 | 주소 | 목록 | 헤더 `<h1>` | 섹션 이름 |
|---|---|---|---|---|
| 오늘 | `/dashboard` | 마감이 오늘이거나 **이미 지난** 미완료 + 마감이 오늘인 완료(취소선) | 오늘 할 일 | 오늘 |
| 전체 | `/dashboard?view=all` | 미완료 전부 | 전체 할 일 | 할 일 |
| 완료 | `/dashboard?view=done` | 완료 전부 | 완료한 일 | 완료 |

- 🔑 **'오늘'은 주소에 싣지 않는다.** 맨 `/dashboard`가 곧 '오늘'이다 — 로그인 착지, 앱 알림의 `?task=`, 히스토리의 `?new=1&from=`처럼 **이미 밖으로 나간 주소가 한 글자도 안 바뀐 채** 산다. 쿼리 순서는 `view → tag → task → new → tags → from → error`이고, '오늘'이면 `view`가 빠져 뒤의 모양이 예전과 같다. 모르는 `view` 값은 '오늘'로 합류한다.
- **'오늘'의 "오늘"은 계정 시간대의 하루다**(`profiles.timezone`, 설계 결정 19) — `[오늘 0시, 내일 0시)`. 날짜만 있는 마감은 그날 23:59:59라 그 안에 든다. 경계는 `lib/time.ts`의 `dayBounds`가 한 번 재고, 쿼리는 `listTasks`의 `today`가 건다. `describeDue`의 `today`(아직 안 지난 오늘)로 대신하지 않는다 — 오늘 이미 지난 마감이 빠진다.
- **"오늘 완료한 것 전부"는 넣지 않는다**(사용자 결정 2026-09-25) — 태스크에 완료 시각이 없다.
- **정렬은 그대로다**(`DASH-1`) — 미완료가 먼저, 각각 마감 임박 순, 마감 없는 것은 끝. '오늘'에서는 미완료 뒤에 오늘 마감인 완료가 선다.
- **강조는 행이 자기 상태로 정한다.** 전에는 섹션이 정했는데('할 일'은 강조, '완료'는 아님), '오늘'에 둘이 섞이면서 행으로 내려갔다. 완료 행은 어느 보기에서든 `data-due`가 없고 제목에 취소선이다.
- 📜 `L-P1-10` 전에는 한 화면에 '할 일'과 '완료' 두 섹션을 위아래로 두었다("자리가 고정돼야 완료가 없는 것과 안 보여 주는 것이 구분된다"). 이제 그 구분은 **메뉴가 말한다** — 무엇을 보고 있는지가 `aria-current`와 헤더 제목에 있다.

**태그 필터**(`DASH-2`)는 **사이드바 안, 보기 메뉴 아래에 있고 고른 보기를 다시 좁힌다**(`L-DS-03`에 사이드바로, `L-P1-10`에 보기 아래로). 태그 링크는 지금 보기를 나른다(`?view=all&tag=…`). **태그가 '미분류' 하나뿐이면 구획째 숨긴다** — 거를 것도 관리할 것도 없다('미분류'는 이름 변경·삭제·병합 출발이 막혀 있다). 피드백이 본 "전체/미분류"가 그 모습이었다. `[전체]` + 태그 이름들이고, 고른 것이 **URL에 실린다** — `/dashboard?tag=<uuid>`. 클라이언트 상태를 만들지 않으므로 주소만으로 같은 화면을 다시 연다. ⚠️ **쿼리 이름이 API와 다르다**: 화면은 `tag`, API(`GET /api/v1/tasks`)는 `tagId`. 주소창은 사람이 치는 자리라 짧은 쪽을 골랐다. 값이 UUID가 아니거나 여러 개면 **400이 아니라 무시하고 전체를 보여 준다.** 고른 칩에 `aria-current="page"`가 붙는다.

**강조는 두 단계다**(`DASH-1`). 요구사항은 "오늘 마감이거나 마감이 지난 것"을 함께 묶었지만 사용자에게 뜻이 다르다 — 이미 늦은 것과 아직 시간이 있는 것.

| 단계 | 조건 | 표시 | 색 |
|---|---|---|---|
| 마감 지남 | `dueAt < 지금` | `마감 지남 · 9월 20일 (일) 09:00` | **진한 빨강** (`text-overdue`) |
| 오늘 마감 | 사용자 시간대로 같은 날, 아직 안 지남 | `오늘 마감 · 9월 23일 (수)` | **빨강** (`text-urgent`) |
| 그 밖 | — | `9월 25일 (목) 18:00` | 회색 (`text-ink-secondary`) |
| 마감 없음 | `dueAt`이 null | (아무것도 그리지 않는다) | — |
| 완료 섹션 | — | 접두사 없이 날짜만 | 옅은 회색 |

- **오늘이면서 이미 지난 마감은 '마감 지남'이다.** 둘 다 강조 대상이라 어느 쪽을 골라도 강조는 걸리고, 갈리는 것은 어느 색이 더 급한 사실을 말하느냐다. 날짜만 있는 마감이 그날의 끝(23:59:59)에 놓인 덕분에([`03-Architecture.md`](03-Architecture.md) §설계 결정 14) 날짜 마감은 그날 내내 '오늘 마감'으로 남고 자정에 넘어간다.
- **강조는 미완료에만 건다.** 완료된 태스크에 "마감 지남"은 거짓이다.
- **접두사를 글자로도 말한다.** 색만 쓰면 색각 이상 사용자에게 강조가 전달되지 않는다. 절대 날짜는 접두사 뒤에 그대로 남아 모든 행의 같은 자리에 온다.
- **판정과 표시의 기준 시간대는 `profiles.timezone`이다** — 서버가 그린다(설계 결정 19). 캡처 API가 이 값을 갱신한다([`04-API-Contract.md`](04-API-Contract.md) §캡처).
- `dueHasTime`이 `false`면 **시각을 그리지 않는다.** 해가 다를 때만 연도를 붙인다(`2027년 1월 3일 (일)`).

**마크업 계약** — 각 행에 `data-due="overdue|today|upcoming|none"`을 싣는다(완료 섹션에는 속성 자체가 없다). 분류를 스타일이 아니라 마크업에 적어야 팔레트를 바꿔도 검증이 살아남는다. 태스크 제목은 `<h3>`, 태그는 `<span>`이다 — 태그를 `<li>`로 그리면 목록 순서를 보는 검증이 태그까지 잡는다.

**주황이 빨강 두 단계가 됐다** (`L-DS-03`, 2026-09-24). 디자인 키트의 팔레트에는 주황이 없고, 키트는 마감 당일과 지남을 **둘 다 `error-600`** 으로 묶는다. 두 단계를 색으로도 가른다는 위의 결정은 그대로 두되 수단을 바꿨다 — 같은 빨강 램프의 한 단계 아래(`error-700`)를 '지남'에 준다. 새 색조를 들이지 않으면서 "이미 늦었다"가 "오늘까지다"보다 진하다는 순서도 맞고, 흰 카드 위 대비가 7.3 / 5.0 / 5.4로 전부 AA다. 값과 근거는 [`08-Design-System.md`](08-Design-System.md).

**사이드바 조판 (`L-DS-03`에서 확정)** — 왼쪽에 인디고 사이드바(240px), 오른쪽에 본문이다. 사이드바에는 Tide 락업(반전) · 태그 필터 · 계정 이메일 · [로그아웃]이 들어가고, 본문 헤더에는 `<h1>`과 [+ 새 태스크]가 남는다.

- 📜 **목업의 네비를 그대로 베끼지 않았다** (`L-DS-03`). 키트 목업의 사이드바는 `오늘 / 전체 / 확인 필요 / 완료 / 설정`인데 도치에는 '오늘'도 '확인 필요'도 **없었다** — 상태는 `todo`/`done` 둘뿐이고 신뢰도 지표를 두지 않는 것이 제품 규칙이다. 없는 개념을 화면이 발명하지 않는다. → 🔁 **`L-P1-10`에서 뒤집혔다.** 판단은 옳았고, 개념이 **요구사항으로 생겼다** — 보기(`DASH-9`)와 확인 필요(`DASH-11`, 생성이 실패한 캡처이지 신뢰도 지표가 아니다). 상태는 여전히 둘이다 — 보기는 상태가 아니라 같은 두 상태를 자르는 방식이다.
- 🔴 **`<nav aria-label="태그 필터">`는 화면에 정확히 하나다.** 좁은 화면용과 넓은 화면용을 따로 그리면 Playwright strict mode가 둘을 잡아 필터 검증이 전부 깨진다. 마크업은 하나로 두고 `lg:` 분기로만 칠한다.
- **1024px 아래에서는 사이드바가 위쪽 가로 막대로 접힌다.** 240px을 떼어 줄 폭이 없다. 선택 표시의 **왼쪽 흰 3px 선은 이때 그리지 않는다** — 세로 목록에서만 뜻이 통하고, 가로 알약 옆에 붙으면 부스러기처럼 보인다(실제 렌더에서 확인). 좁은 화면에서는 흰색 14% 덮개만으로 말한다.
- **계정 이메일과 로그아웃이 사이드바 하단으로 내려갔다.** 헤더에 두던 이유(제목을 밀지 않게)는 그대로 유효하고, 사이드바는 더 확실한 바깥이다. 🔴 이메일을 반응형으로 **숨기지 않는다** — 보여야 한다는 검증이 있다.
- **인디고 채움 버튼은 본문의 [+ 새 태스크] 하나뿐이다**(키트 3-2). 상세 패널은 별개의 카드라 자기 [저장]을 가질 수 있다.

**행에 붙은 것 둘 (`L-DS-03`)**

- **원형 마감 링 = 완료 표시** — 키트의 원형 체크박스 모양이다. 테두리 색이 마감 단계를 한 번 더 말하고, 완료 행은 인디고로 채운 원 + 흰 체크다. **누르면 완료·미완료가 뒤집힌다**(`DASH-10`, `L-P1-09`). 링 자체는 여전히 `aria-hidden`이고, 그것을 감싼 `<button>`이 이름(`<제목> 완료로 표시` / `<제목> 미완료로 되돌리기`)과 `aria-pressed`를 싣는다. 체크박스가 아니라 버튼인 것은 `getByRole("checkbox")`가 패널의 태그 체크박스만 잡아야 해서다.
  - 🔴 **행 링크(`<a>`) 안에 넣지 않는다**(인터랙티브 중첩 금지). `<li>`가 카드를 입고, 그 안에서 완료 폼과 상세 링크가 **형제**로 선다. 폼 제출이라 클라이언트 컴포넌트가 늘지 않는다.
  - 누른 뒤에는 **누르기 전에 열려 있던 패널로 돌아간다**(폼의 `open`). 행에서 눌렀다고 그 태스크의 패널이 새로 열리지 않는다 — 목록을 훑으며 연달아 체크하는 동선이 끊기지 않게.
  - 📜 `L-DS-03`에서는 "조작할 수 없는 장식, 완료 전환은 패널의 [완료로]"였다. 그때는 행 전체가 `<a>`였기 때문이고, 이번에 버튼과 링크를 형제로 갈라 풀었다.
- **'자동' 배지** — `source`가 `manual`이 아닌 행, 곧 에이전트가 만든 행에 붙는다. 같은 배지가 패널의 '생성 경로' 값에도 씌워져 목록에서 보던 표시가 상세로 이어진다.
- 🔴 **둘 다 `<span>`이다.** `<p>`로 그리면 "행 안 첫 번째 `<p>`가 마감 줄"이라는 전제가 깨져 마감 3색 검증이 엉뚱한 요소를 집는다. 그리고 행에 글자를 더할 때는 **'행에 콜론이 없어야 한다'와 '태그 없는 행에 태그 이름이 없어야 한다'** 두 검증을 먼저 확인한다 — '자동' 두 글자는 그래서 통과했다.

**화면을 보고 고친 것 넷** (`L-P0-11` 디자인 확인, 2026-09-23). 전부 실제 렌더를 보고 판단했다.

- **계정 정보와 로그아웃은 헤더에.** 이메일을 제목과 같은 줄에 두었더니 좁은 화면(390px)에서 제목을 밀어 **"대시 / 보드"로 쪼갰다.** 이메일은 제목 아래 작게 깔고(`truncate`), 로그아웃은 헤더 오른쪽으로 올렸다 — 목록 끝에 두면 태스크의 일부처럼 보인다. 버튼에 `whitespace-nowrap`이 없으면 이번엔 버튼이 "로그 / 아웃"으로 쪼개진다. (`L-DS-03`부터는 `html`의 `word-break: keep-all`이 이 쪼개짐을 뿌리에서 막는다 — 자리마다 `nowrap`을 붙이는 대신 한 번에 말한다.)
- **완료 섹션은 배경으로 눌러 둔다.** 두 섹션을 같은 카드로 그리면 한 덩어리로 읽혀 "여기부터 끝난 것"이 안 보인다. 완료 행은 테두리 없이 회색 배경, 글자도 한 단계 옅게. (`L-DS-03`에서 키트 규칙에 따라 제목에 **취소선**이 더해졌다.)
- **제목이 주인공이다.** 강조된 마감이 색으로 튀는 만큼 제목의 무게를 올린다(`font-medium`). 그러지 않으면 빨간 마감 줄이 태스크 이름보다 먼저 읽힌다.
- **필터 칩과 태그 칩을 갈라 둔다.** 필터는 **누르는 것**, 태그는 **읽는 것**이다. 비슷하게 그리면 태스크에 달린 태그를 눌러 보게 된다 — 필터는 알약(테두리 pill), 태그는 납작한 사각 라벨.

**빈 상태 문구**

| 자리 | 문구 |
|---|---|
| 오늘 | `오늘 마감이거나 마감이 지난 할 일이 없습니다.` |
| 전체 | `할 일이 없습니다. 앱에서 화면을 캡처하면 여기에 쌓입니다.` |
| 완료 | `완료한 태스크가 없습니다.` |
| 어느 보기든 · 태그 필터 있음 | `이 태그에 해당하는 태스크가 없습니다.` |

전역 빈 상태를 따로 두지 않는다 — 안내 문장이 한 화면에 둘이면 어느 것이 이 상황의 설명인지 흐려진다.

## 태스크 상세 패널 (`L-P0-12`에서 확정)

**화면의 모든 상태가 URL에 있다.** 열린 태스크는 `?task=<uuid>`, 새 태스크는 `?new=1`, 태그 관리는 `?tags=1`, 방금 실패한 것은 `?error=<code>`이며 태그 필터(`?tag=`)는 그 위에 함께 실린다. 클라이언트 상태를 만들지 않으므로 이 화면의 `"use client"`는 **1건**(아래 §실시간 반영의 구독 한 줄)뿐이고 그것도 데이터를 들지 않는다. 앱 알림의 딥링크(`NTF-2`)는 따로 만들 것 없이 따라온다.

🔑 **패널 슬롯은 하나다 — `tags` → `new` → `task`** (`L-P1-06`에서 확정). 오른쪽에 설 수 있는 것은 태그 관리·새 태스크·태스크 상세 셋인데 자리가 하나뿐이라 순서가 필요하다. 뜻은 **"방금 누른 것이 이긴다"** 이다: [관리]는 태스크를 열어 둔 채로도 [새 태스크]를 열어 둔 채로도 누를 수 있어 가장 나중의 조작이고, `?task=`는 목록의 행을 누른 결과라 가장 오래됐다.

- 🔴 **우선순위가 적힌 곳은 `app/(app)/dashboard/url.ts`의 `panelOf` 하나다.** 화면에서 `isNew && !isTags` 같은 조건을 다시 조립하지 않는다 — 순서가 두 벌이 되는 순간 두 패널이 동시에 열리고, 바로 아래 `?error=` 규약까지 무너진다. 안 열릴 패널의 데이터도 읽지 않는다(같은 값이 페치를 가른다).
- 🔴 **`?error=` 한 칸을 두 어휘가 나눠 쓴다.** 태스크 패널은 소문자 화면 코드(`title_required`)를 `dashboardMessage()`로, 태그 패널은 대문자 API 사유(`TAG_NAME_TAKEN`)를 `tagErrorMessage()`로 푼다. **안전의 근거는 두 패널이 동시에 서지 않는다는 것**이고, 그것을 보장하는 것이 위의 `panelOf`다. 덤으로 두 어휘가 대소문자로 서로소라 섞여도 오해가 생기지 않는다. 태그 쪽이 API 사유를 그대로 쓰는 이유는 그 문장들이 이미 사용자에게 보내는 완성된 한국어이고 `409` 본문과 같은 표에서 나오기 때문이다(`API-5`) — 소문자 표를 새로 만들면 같은 뜻이 두 벌이 된다.
- `?task=`가 UUID가 아니거나, 없거나, 남의 것이면 **세 경우가 같은 패널**로 합류한다: `태스크를 찾을 수 없습니다. 삭제되었을 수 있습니다.` 구분해 주면 id를 넣어 보는 것만으로 남의 태스크가 실재하는지 알아낼 수 있다(API의 404 규칙과 같은 태도).
- **태그 필터 칩은 `task`를 나르지 않는다.** 필터를 바꾸면 열려 있던 태스크가 목록에서 사라질 수 있다.
- 📮 **목록에 없는 `?tag=`는 빈 목록을 낸다** — 손으로 친 죽은 id가 그렇고, 사이드바에는 짚이는 항목이 하나도 없다([전체]조차 안 짚인다). 태그 관리가 이것을 일상 동선으로 만들 뻔했지만 **액션이 고친다**(아래 §태그 관리 패널). 화면에서 막지 않은 것은 그러려면 태그 목록을 먼저 `await` 해야 해 `Promise.all`이 깨지기 때문이다.

**패널의 6개 항목**(`DASH-3`)은 위아래 두 덩어리로 나뉜다. 값이 없어도 **자리를 지운 적이 없다** — 데이터에 따라 항목 수가 흔들리면 "6개"가 검증할 수 없는 말이 된다.

| 덩어리 | 항목 | 모양 |
|---|---|---|
| 사용자가 고친다 | 제목 · 설명 · 마감일 · 태그 | 늘 편집 가능한 폼 + **[저장]**. 보기/편집 모드를 나누지 않는다 |
| 사실을 읽는다 | 상태 · 근거 · 생성 경로 | 읽기 전용. 상태는 회색 필로 **보여 주기만** 한다 |

- **완료 전환은 제목 앞의 완료 표시다**(`L-P1-09`). 행과 **같은 물건**이 패널 머리의 "태스크 상세" 앞에 선다. 옛 [완료로]·[할 일로] 버튼은 없앴다. 패널에서는 이름에 제목을 붙이지 않는다(`완료로 표시` / `미완료로 되돌리기`) — 버튼이 하나뿐이고, 붙이면 제목에 "제목"이 든 태스크에서 `getByLabel("제목")`이 입력 칸과 버튼을 함께 잡는다(실제로 깨졌다).

**태그는 한 줄짜리 단일 선택 + '새 태그' 입력이다** (HF-10, 2026-09-29). 경위: HF-03(2026-09-26)에서 태그 수만큼 서던 체크박스 줄을 통째로 뺐는데 — 태그가 늘수록 제목·설명·마감을 아래로 밀어냈다 — 그러자 **웹에서 태그를 고칠 곳이 사라졌고**, 에이전트가 '미분류'로 보낸 태스크는 영영 '미분류'였다(QA 보고). 체크박스로 되돌리지 않고 `<select aria-label="태그">` 하나로 되살렸다 — 태스크 대부분은 태그가 하나다. 바로 아래 `새 태그`(`aria-label`, 선택 입력)가 채워지면 select보다 이긴다: 그 이름의 태그를 만들어(이미 있으면 그것을) 건다. **태그가 '미분류'뿐인 계정은 이 칸이 없으면 고를 것이 없다.**

- ⚠️ **단일 선택이 여러 태그를 하나로 줄이지 않게.** 에이전트는 태그 둘을 달 수 있고 `patchTask`는 `tagIds`가 오면 그대로 덮어쓴다. 그래서 폼이 처음 골라져 있던 값(`tagOriginal`)을 함께 보내고, **select가 그대로면 `tagIds` 키를 싣지 않는다.** `e2e/task-panel.spec.ts`의 *"태그가 둘인 태스크를 제목만 고쳐 저장해도 태그 둘이 다 남는다"* 가 매번 확인한다. 태그 없는 태스크(예전에 직접 만든 것)는 '미분류'가 골라진 채 열리지만 같은 규칙으로 여는 것만으로 태그가 붙지 않는다.
- 폼 이름이 `tagId`인 것은 `tag`를 필터를 나르는 hidden input이 이미 쓰고 있어서다.
- 🌐 **API는 그대로다.** `PATCH /api/v1/tasks/{id}`의 `tagIds`는 계약 그대로고, 웹 폼이 그것을 다시 쓸 뿐이다. `POST /api/v1/tags`는 `lib/api/tags.ts`의 `createTag`로 옮겼을 뿐 응답은 한 글자도 안 바뀌었다.

- **마감은 날짜 칸과 시각 칸 둘이다.** 시각이 없는 마감에 `23:59`를 채워 두지 않는다 — 채우면 사용자가 저장만 해도 '시각이 있는 마감'으로 바뀐다(설계 결정 14). **날짜 없이 시각만 고르면 조용히 버리지 않고 알린다**(`마감 시각만으로는 저장할 수 없습니다. 날짜를 함께 골라 주세요.`). 버리면 마감을 넣었다고 믿게 된다.
- **근거가 없으면**(직접 추가한 태스크) `에이전트가 남긴 근거가 없습니다.`
- **생성 경로는 enum 값이 아니라 한국어다** — `캡처 (생성)` · `캡처 (완료)` · `메일` · `직접 추가`.
- 폼이 셋인 것은 HTML이 폼 중첩을 금지해서다. [저장]·완료 표시·[삭제]는 보내는 것이 서로 다르다.

**실패는 URL이 나른다**(`?error=`). 인증 화면과 같은 방식이고 같은 대가를 치른다 — **입력이 날아간다.** 살리려면 `useActionState`가 필요하고 그것은 클라이언트 컴포넌트를 부른다. 여기까지 오는 실패는 제목이 공백뿐(잃을 입력이 없다), 날짜 없이 시각만, 다른 탭에서 태스크나 고른 태그가 지워진 경우뿐이라 감수한다. (마지막은 HF-10에 태그 칸이 돌아오며 다시 생겼고 `입력을 확인해 주세요.`로 뜬다.)

**조판 (`L-DS-03`에서 확정)** — 패널은 흰 카드 하나다(폭 320px, 키트의 오버레이 카드와 같은 값). 읽기 전용 세 항목의 값이 달라졌다: **상태**는 회색 필, **생성 경로**는 에이전트가 만든 것이면 목록의 행과 **같은 '자동' 배지**이고 사람이 만든 것이면 회색 필이다. [삭제]는 채우지 않은 빨간 글자 버튼이다 — 채우면 화면에 인디고가 아닌 채움 버튼이 하나 더 생긴다.

🔴 **`<dt>`의 글자는 그대로 둔다.** "마감일"·"상태"·"근거"·"생성 경로" 네 라벨은 글자가 정확히 일치해야 하는 검증이 걸려 있어 콜론도 아이콘도 한 글자 붙일 수 없다. 꾸밀 것이 있으면 `<dd>` 쪽에 붙인다.

**화면을 보고 고친 것 셋** (`L-P0-12` 디자인 확인, 2026-09-23). 전부 실제 렌더를 보고 판단했다.

- 🔴 **좁은 화면에서는 패널이 목록 위로 온다.** 아래에 두었더니 390px에서 행을 눌러도 **화면에 아무 변화가 없어 보였다** — 패널은 스크롤 한참 아래에 생겼다. `flex-col-reverse lg:flex-row`로 모바일에서만 순서를 뒤집는다.
- **열린 행을 목록에서 짚어 준다.** 패널만 바뀌면 여러 행 중 어느 것을 보고 있는지 알 수 없다. 필터 칩과 같은 표지(`aria-current="page"`)에 진한 테두리.
- **미완료 행의 hover에 회색 배경을 쓰지 않는다.** 완료 행의 기본 배경이 `bg-gray-50`이라, 미완료 행에 마우스를 올리는 순간 완료된 것처럼 보였다. hover는 배경이 아니라 **테두리**로 말한다.

## 태그 관리 패널 (`L-P1-06`에서 확정)

`/dashboard?tags=1` — 사용자가 태그 이름을 바꾸고, 다른 태그로 바꾸고(병합), 지운다(`DASH-6`의 화면 쪽). **새 화면을 만들지 않는다.** 위 §태스크 상세 패널과 같은 슬롯을 쓰고 순서는 거기 적힌 대로다.

**진입점은 사이드바 태그 구획의 [관리]** 다(사용자 결정 2026-09-24). 고칠 대상이 눈앞에 있는 자리이고, 본문 헤더에 두면 인디고 채움 버튼이 둘로 보이거나 헤더가 붐빈다. 링크는 **현재 태그 필터를 나른다**(`?tag=<id>&tags=1`).

| 자리 | 내용 |
|---|---|
| 거절 배너 | `?error=`가 있을 때만. 패널 **위 하나**다 |
| 태그 한 줄 | `[이름 입력] [저장] [삭제]` — `<li data-tag-id>` 안의 **폼 둘**(HTML이 폼 중첩을 금지한다) |
| '미분류' 줄 | 이름만. 폼이 없다 |
| 태그 바꾸기 | `기존 태그` · `바꿀 태그` 두 `<select>` + [바꾸기]. 고를 것이 없으면 통째로 그리지 않는다 |

- **'미분류'는 행을 그리되 폼만 뺀다.** 목록에서 지우면 사이드바 필터에는 보이는 태그가 여기엔 없어 "내 태그가 아닌가"가 된다. 🔴 **"(보호됨)" 같은 글자를 붙이지 않는다** — 행 글자가 늘면 목록 텍스트를 보는 검증 표면이 는다.
- **동작은 병합(API `merge`)이지만 화면 어휘는 찾기/바꾸기다**(HF-12, 사용자 피드백 2026-09-29). 처음엔 '태그 합치기' + '없어질/남을 태그'였는데 "합치기"가 비직관적이라는 피드백이 왔다 — 사용자는 오피스 앱의 [바꾸기]에 이미 익숙하고, "기존 태그를 바꿀 태그로"라는 한 문장이 방향과 사라지는 쪽을 함께 말한다. 둘째 칸을 피드백 원안의 '신규 태그'로 쓰지 않은 것은 **이미 있는 태그를 고르는 칸**이라서다 — 새 태그가 생긴다고 읽히면 안 된다(사용자 결정). API `message`(`합칠 태그를 선택해 주세요.` 등)는 `public/api.md` 계약이라 그대로 둔다.
- **보호는 출발에만 건다.** '미분류'는 '기존 태그' 목록에 없고 '바꿀 태그'에는 있다 — 대칭이 아닌 것이 의도다([`04-API-Contract.md`](04-API-Contract.md) §태그 합치기).
- **삭제에 확인 단계를 두지 않는다.** 태스크는 남고 연결만 떨어지므로 잃는 것은 분류뿐이고(`e2e/tags.spec.ts`가 실증한다), 태스크 패널의 [삭제]도 확인이 없다. 확인을 넣으면 `L-P1-07`이 탈퇴에 쓸 진짜 2단계와 무게가 같아 보인다.
- **거절 배너는 행 안이 아니라 패널 위 하나다.** 히스토리가 문구를 항목 안에 넣은 이유는 *"100건까지 쌓이는 화면에서 상단 배너는 어느 것이 거절됐는지 말해 주지 못한다"* 였는데, 태그는 한 줌이고 `TAG_NAME_TAKEN`은 방금 타이핑한 그 행이라 애매하지 않으며 **병합 실패는 애초에 주인 행이 없다.** 근거가 넘어오지 않으므로 따라가지 않는다.
- 📮 **이름 변경 실패는 입력을 잃는다.** `?error=`로 도는 동안 타이핑한 이름이 날아가고 옛 이름이 돌아온다 — §태스크 상세 패널이 이미 감수한 대가와 같다(살리려면 `useActionState`, 그건 `"use client"`다).

**사라진 태그를 보고 있었다면 액션이 필터를 고친다.** 그대로 두면 빈 목록에 갇히고 어느 필터인지도 알 수 없다.

| 조작 | `?tag=`가 그 태그였다면 |
|---|---|
| 삭제 | **푼다**(전체로) — 그 태그의 태스크가 어디로 간 것이 아니라 분류만 없어졌다 |
| 병합 | **도착을 따라간다** — 보던 태스크들이 그 자리에 그대로 있고 태그 이름만 바뀌었다 |
| 이름 변경 | 그대로 — id가 안 바뀐다 |

**마크업 계약** — `<li data-tag-id>`. 같은 글자의 [저장]·[삭제] 버튼이 태그 수만큼 생기므로 검증이 **행으로 스코프**한다(히스토리의 `data-log-id`가 [되돌리기] N개를 다루는 것과 같다). 🔴 `components/ui.tsx`의 `Button`에 `aria-label`을 열지 않는다 — 버튼 문구가 계약이라 일부러 막아 둔 것이고, 접근 이름이 보이는 글자와 달라지면 음성 조작이 깨진다(WCAG 2.5.3).

- 이름 입력만 `aria-label`(`"<태그 이름> 이름"`)을 쓴다. `Field`로 감싸면 라벨 줄이 태그 수만큼 생겨 320px 패널이 세로로 두 배가 된다 — 마감 두 칸이 쓰는 것과 같은 비대칭이다. 이름이 유일한 것은 `(user_id, name)` 유니크가 보증한다.
- 🔴 **`<select>`에도 `aria-label`을 따로 준다.** `<label>`이 `<select>`를 감싸면 접근 이름이 라벨의 텍스트 **전체**가 되는데 거기에 모든 `<option>` 글자가 섞여 든다(실측: `없어질 태그태그를 고르세요업무학업…` — HF-12 전 라벨). 그러면 `getByLabel("바꿀 태그")`가 옵션에 그 글자를 가진 다른 select까지 집는다. **`<input>`에는 없던 문제가 `<select>`에서 처음 생겼다.**

**조판** — 저장소의 **첫 `<select>`** 다. 네이티브를 그대로 쓰고 `appearance-none` + 커스텀 셰브론을 하지 않는다: 클라이언트 JS 0으로 키보드 조작과 모바일 휠 피커까지 주는 유일한 컨트롤이다. 🔴 **빈 값의 첫 `<option>`("태그를 고르세요")이 있어야 `required`가 작동한다**(HTML의 *placeholder label option*). 빠뜨리면 브라우저 검증이 조용히 꺼져 손대지 않고 눌러도 첫 태그끼리 병합을 시도한다. 서버 검증은 그대로 두는데 이중이 아니라 **층이 다르다** — 브라우저 검증이 꺼진 경우의 뒷문이다.

**화면을 보고 고친 것 하나** (`L-P1-06` 디자인 확인) — `<legend>`(당시 "태그 합치기")와 첫 라벨이 **딱 붙어 보였다.** `fieldset`에 `gap-3`을 주었지만 legend는 flex 흐름 밖이라 걸리지 않는다. 간격을 legend에 직접 줬다.

## 실시간 반영 (`L-P0-13`에서 확정)

에이전트가 태스크를 만들거나 완료하면 **사용자가 아무것도 하지 않아도 화면이 따라온다**(`DASH-5`). 구현은 [`03-Architecture.md`](03-Architecture.md) §설계 결정 21.

**무엇이 보이는가** — 화면이 새로 그려지는 것이지 행 하나가 끼어드는 것이 아니다. 목록 전체가 서버 기준으로 다시 정렬·강조되고 태그 칩도 함께 온다. 스크롤 위치와 열려 있던 패널은 그대로다.

| | 반영된다 | 반영되지 않는다 |
|---|---|---|
| 내 태스크의 생성·완료·수정 | ✅ 즉시 | |
| 캡처 한 장이 만든 여러 건 | ✅ **한 번에 함께** 나타난다(0.2초로 접는다 — 한 건씩 늘어나는 모양을 보여 주지 않는다) | |
| 다른 탭·앱에서 지운 태스크 | | ❌ 지운 쪽 화면만 갱신된다 |
| 다른 탭에서 **태그만** 바꾼 저장 | | ❌ 태스크 행이 변하지 않아 신호가 없다 |
| 남의 태스크 | | ❌ 애초에 구독하지 않는다 |

**편집 중이어도 입력을 잃지 않는다.** 패널의 칸은 전부 uncontrolled(`defaultValue`)이고 갱신은 리마운트가 아니라 재조정이라, **사용자가 손댄 칸은 그대로 남고 안 건드린 칸만 새 값으로 바뀐다.** 예외는 보고 있던 태스크가 다른 곳에서 지워진 경우인데, 삭제는 구독하지 않으므로 실시간으로는 일어나지 않는다.

## 앱 셸 (`L-P1-03`에서 확정)

로그인한 화면들(`/dashboard`·`/history`·`/settings`)이 **한 벌의 껍데기**를 나눠 쓴다. 인디고 사이드바 + 본문 2단이고, 조판 값은 위 §사이드바 조판 그대로다.

사이드바는 위에서부터 **Tide 락업 · 주요 메뉴 · 화면별 조각 · 전역 단축키 · 계정 이메일 + [로그아웃]** 이고, 구획마다 흰색 14% 가로선이 갈라 준다. 본문 헤더에는 `<h1>`과 그 화면의 주 행동이 남는다(대시보드는 [+ 새 태스크], 히스토리·설정은 없다).

**주요 메뉴**(`<nav aria-label="주요 메뉴">`)는 **`오늘 / 전체 / 확인 필요 / 완료 / 히스토리` + 구분선 + `설정`** 이다(`L-P1-10`·`L-P1-12`, 목업의 순서). '확인 필요'에만 **개수 배지**가 붙는다(아래 §확인 필요). 지금 화면(대시보드는 지금 보기)에 `aria-current="page"`가 붙는다. 보기는 한 화면의 `?view=`라 `AppShell`의 `current`는 경로가 아니라 **항목 키**다. 히스토리는 되돌리기와 앱 알림의 도착지라 남는다(사용자 결정 2026-09-25).

- 📜 **목업의 네비를 그대로 베끼지 않았다** (`L-P1-03`~`L-P1-07`). 그때 목업의 항목 중 도치에 있던 것은 `설정` 하나뿐이었고, 규칙은 "**실제로 있는 화면만 적는다**"였다. → 🔁 **`L-P1-10`에서 뒤집혔다** — 규칙은 그대로이고, 보기와 확인 필요가 요구사항(`DASH-9`·`DASH-11`)으로 **실제로 생겼다.** 위 §사이드바 조판의 같은 항목 참고.
- **주요 메뉴 항목과 태그 필터 항목은 같은 모양이다.** 둘 다 "누르면 화면이 바뀌는 것"이고, 모양을 가르면 같은 뜻의 선택 표지가 두 벌이 된다. 무엇을 고르는 네비인지는 `<nav>`의 이름과 사이에 놓인 구분선이 말한다. 구현은 `components/ui.tsx`의 `SidebarLink` 하나다.
- **태그 필터는 대시보드에만 있다.** 히스토리에는 태그라는 개념이 걸리지 않는다 — 없는 개념을 화면이 발명하지 않는다는 위의 규칙이 여기에도 적용된다. 🔴 `<nav aria-label="태그 필터">`는 **대시보드에 정확히 하나**이고 히스토리에는 **0개**다.
- **태그 구획에 머리줄이 있다**(`L-P1-06`) — 왼쪽에 `태그`, 오른쪽에 [관리]. 제목은 아래 '전역 단축키'와 **같은 `text-label`** 이다(2026-09-26에 맞췄다) — 나란히 선 두 구획의 제목이 서로 다른 크기면 위계가 어긋나 보인다. `L-P1-03`이 관찰한 것을 닫은 것이다: 주요 메뉴의 '대시보드'와 태그 필터의 '전체'가 같은 흰 덮개를 달고 나란히 서서 **위계가 평평해 보였다.** 구분선만으로는 두 구획이 다른 축이라는 것을 말하지 못한다. 선례는 바로 아래 '전역 단축키' 구획이고 그쪽도 `<section aria-label>` + 같은 글자의 머리줄이다.
  - **구획은 접혀 있다**(HF-12, 사용자 피드백 2026-09-29) — 태그가 늘면 사이드바가 길어져 [로그아웃]이 첫 화면 밖으로 밀렸다(HF-04와 같은 증상). 머리줄이 네이티브 `<details>`의 `<summary>`라 클라이언트 JS가 없다. **태그를 골라 둔 화면은 펼친 채로 그린다** — 접어 두면 본문이 왜 좁혀졌는지가 사라진다. 🔴 [관리]는 `<details>` **밖** 형제로 두고 머리줄 오른쪽에 겹친다 — 닫힌 `<details>`는 `<summary>` 말고 모든 자식을 숨겨, 안에 두면 접혔을 때 [관리]도 사라진다. 🔴 닫힌 구획 안의 "태그 필터" 네비는 접근성 트리에서 빠지므로 검증은 `e2e/support/ui.ts`의 `openTagFilter`로 먼저 편다.
  - 🔴 **머리줄은 `<nav>` 바깥이다.** [관리]는 필터가 아니라 패널을 여는 행동이라 안에 넣으면 "태그 필터" 목록에 필터 아닌 항목이 섞이고, `<nav>`가 하나라는 위의 규칙도 흐려진다.
  - 🔴 **[관리]에 `buttonClass("text")`를 쓰면 안 보인다.** 그 톤은 `text-brand`(인디고)인데 사이드바 면도 `bg-brand`다 — 빌드도 lint도 grep 게이트도 잡지 않고 **렌더만 사라진다.** 인디고 면 위에서 누르는 것은 `ON_BRAND_QUIET` 하나뿐이다([로그아웃]이 쓰는 것).

**전역 단축키 구획**(`<section aria-label="전역 단축키">`)은 앱이 쓰는 두 조합을 보여 준다 — 앱에는 단축키를 알려 줄 자리가 없고(로그인 화면에만 있다) 웹뷰가 이 사이드바를 그대로 띄운다.

- 🔴 **철자가 계약이다** — 앱의 표기(`HotkeyConfig.shortcutDisplay`)와 한 글자도 달라서는 안 된다. 앱 창 안에서는 두 표기가 나란히 보여, 다르면 사용자에게 **서로 다른 조합처럼 읽힌다.** 지금 값은 `Shift+⌘+1`·`Shift+⌘+2`(macOS) / `Ctrl+Shift+1`·`Ctrl+Shift+2`(Windows)이고, **고치려면 앱 부서에 먼저 알린다**(HF-02, 2026-09-25).
- **한 번에 한 플랫폼만 보여 준다.** 머리줄 옆의 [macOS]·[Windows] 두 버튼이 고르고, 줄은 언제나 둘(`새 태스크`·`완료`)이다. 240px 사이드바에 두 플랫폼을 나란한 열로 두면 `Ctrl+Shift+1` 길이에서 `새 태스크`가 쪼개지고, 세로로 쌓으면 구획이 두 배가 된다.
- 🔴 **머리줄은 한 줄이다** — 왼쪽에 제목, 오른쪽에 두 버튼(`justify-between`, 줄바꿈 없음). 위 태그 구획의 `태그`/[관리]와 같은 짜임이고 제목도 같은 `text-label`이다. **버튼의 보이는 글자는 `mac`·`Win`으로 줄이고 `aria-label`이 전체 이름을 든다.** 머리줄이 쓸 수 있는 폭은 184px(240 − 셸 패딩 32 − 구획 패딩 24)뿐이라 전체 이름으로는 189px(폰트가 아직 안 온 대체 글꼴에서는 192px)이 되어 `flex-wrap`이 버튼을 제목 아래로 떨어뜨렸다 — **"옆에 둔다"고 쓴 배치가 실제로는 아래 한 줄로 보였다**(사용자 보고 2026-09-26, 실측으로 확인). 줄인 이름이면 대체 글꼴에서도 158px이다. WCAG 2.5.3은 지킨다(접근 이름이 보이는 글자를 포함한다).
- **처음 보여 줄 쪽은 서버가 요청 헤더로 고른다** — 윈도우에서 띄운 앱은 Windows가, 맥에서 띄운 앱은 macOS가 먼저 보인다. 고른 값은 저장하지 않는다(화면을 옮기면 자기 플랫폼으로 돌아온다). 근거는 [`03-Architecture.md`](03-Architecture.md) §설계 결정 28.

**계정 이메일 + [로그아웃]은 단축키 구획 바로 밑이다** (HF-04, 2026-09-26). 그 전에는 `lg:mt-auto`로 사이드바 맨 아래에 붙여 두었는데, **사이드바가 본문과 같은 높이로 늘어나므로 긴 화면('전체'·히스토리)에서는 둘이 페이지 맨 밑까지 내려가 로그아웃하려면 스크롤을 해야 했다**(사용자 보고).

- **[로그아웃]은 아이콘 전용이다.** 버튼은 40px 정사각형, 아이콘은 24px — HF-10(QA 요청)에 32px/18px에서 키웠고 모양도 QA가 건넨 원본(`tide-icon-logout.svg`)으로 바꿨다. 클래스는 `ON_BRAND_QUIET`에 덧대지 않고 `ON_BRAND_ICON`을 따로 둔다(같은 프로퍼티를 두 번 적으면 어느 쪽이 이길지 모른다). 글자 네 자가 차지하던 폭이 이메일로 간다 — 240px 사이드바에서 `iamjuankim@g…`로 잘리던 주소가 다 들어간다. 접근 이름은 `aria-label`이 들고 아이콘 자신은 언제나 `aria-hidden`이라, `getByRole("button", { name: "로그아웃" })`을 쓰는 검증 다섯이 그대로 산다. 그래도 잘리는 긴 주소는 `title`로 확인한다(`<p>`의 `title`은 접근 이름에 끼어들지 않는다).
- **아이콘은 키트에 없어 우리가 그렸다** — 같은 규칙(24 그리드 · stroke 1.8 · 둥근 끝)으로 열린 문 모양의 괄호와 밖으로 나가는 화살표. `components/icons.tsx`의 `logout`이다.
- 🔴 **위치는 좌표로 검증한다**(`e2e/history.spec.ts`). 클래스(`lg:mt-auto`)를 보면 스타일을 바꿀 때마다 깨지고, `toBeVisible`만 보면 **뷰포트 밖이어도 통과한다** — 이 고장이 정확히 "보이긴 하는데 한참 아래"였다.

**🔑 이 껍데기는 `layout.tsx`가 아니라 컴포넌트(`app/(app)/shell.tsx`)다.** Next 16의 레이아웃은 네비게이션에서 다시 그려지지 않아 `pathname`도 `searchParams`도 읽을 수 없는데, 사이드바가 그려야 하는 두 표지가 정확히 그 둘에 걸려 있다 — 주요 메뉴의 `aria-current`(경로)와 태그 필터의 선택(`?tag=`). 근거와 대가는 [`03-Architecture.md`](03-Architecture.md) §설계 결정 26.

## 확인 필요 (`L-P1-12`에서 확정)

`/dashboard?view=review` — 생성이 실패한 캡처 중 사용자가 아직 처리하지 않은 것(`DASH-11`). **신뢰도가 낮은 항목이 아니다** — 에이전트는 여전히 되묻지 않고, 여기 오는 것은 태스크를 **만들지 못한** 캡처뿐이다. 범위(`NO_TASK_TO_CREATE`·`AGENT_TIMEOUT`·`INTERNAL_ERROR`, 중복은 뺀다)는 `lib/api/job-logs.ts`의 `NEEDS_REVIEW` 한 곳이고 경위는 [`03-Architecture.md`](03-Architecture.md) §설계 결정 29.

| 자리 | 모양 |
|---|---|
| 사이드바 배지 | '확인 필요' 오른쪽 흰 원에 `secondary-700` 숫자(키트 4-3, 10.6:1). **0이면 그리지 않는다** — 받은편지함처럼 비워지는 목록이라 0은 "할 일 없음"이고, 배지가 서 있으면 그 자체가 할 일로 읽힌다. 접근 이름에 숫자가 붙는다("확인 필요 2"). **모든 화면**에 선다(셸이 센다) |
| '오늘' 배너 | 목록 위 넓은 배너 — `attention-*` 면 + 경고 아이콘 + "확인이 필요한 캡처가 N건 있어요" + Text 버튼 [보기]. 0건이면 없다. `role="status"`. **흐름 안의 블록**이라 z-index가 필요 없다 |
| 항목 | 히스토리와 같은 재료 — 시각 · 요약(없으면 `캡처 내용이 기록되지 않았습니다.`) · 사유 문장(`failureSentence`, 히스토리와 한 벌). 버튼은 [넘기기]·[직접 처리] 둘, 둘 다 2차 |
| 빈 상태 | `확인할 캡처가 없습니다. 에이전트가 만들지 못한 캡처가 생기면 여기에 모입니다.` |

- **[직접 처리]는 이 보기를 나른다** — `/dashboard?view=review&new=1&from=<logId>`. 저장하면 이 목록으로 돌아와 방금 만든 태스크의 패널이 열리고, 항목은 빠져 있다. 패널을 열고 닫기만 하면 남는다(처리 표시는 저장 성공 뒤에만).
- **[넘기기]는 아무것도 지우지 않는다** — 처리 표시만 하고, 히스토리에는 그대로 남는다.
- 🔑 **건수는 이동할 때 갱신된다**(사용자 결정 2026-09-25). 실시간 구독은 여전히 `tasks`만 본다(설계 결정 21) — 켜 둔 화면에서 캡처가 실패해도 배지는 다음 이동 때 오른다. 실패는 앱이 OS 알림으로 이미 말하므로 놓치지 않는다. 즉시가 필요해지면 구독을 `job_logs`로 넓히는 것은 **더하는 변경**이다.
- 배지와 배너는 같은 인디고라 **모양으로** 가른다(키트 3-4) — 배너는 넓고 아이콘이 붙고, '자동'은 점이 붙은 작은 배지다.

## 히스토리 (`L-P1-03`에서 확정)

`/history` — 에이전트가 무슨 일을 했는지를 **최신순 100건**으로 읽는다(`HIST-1`). 앱과 같은 데이터·같은 정렬이다(`GET /api/v1/job-logs`와 같은 함수를 부른다).

기록 한 건이 그리는 것, 위에서 아래로:

| 자리 | 내용 |
|---|---|
| 머리줄 | `<time datetime>`(사용자 시간대로 `9월 24일 (목) 13:00`) · 소스 라벨 · **결과 필** |
| 요약 | `capture_summary` 한 줄. 캡처 원본이 남지 않으므로(`AGT-10`) 무엇을 보고 한 일인지 말해 주는 것은 이 한 줄뿐이다 |
| 실패 사유 | 실패 기록에만. 빨간 글자 |
| 근거 | 완료 기록의 `rationale`. 완료 오판을 교정하려면 왜 닫았는지를 읽어야 한다 |
| 관련 태스크 | `관련 태스크` + 제목 링크들. 누르면 `/dashboard?task=<uuid>`로 가 상세 패널이 열린다 |

- **소스와 결과는 축이 다르다.** 소스(`캡처 (생성)`·`캡처 (완료)`·`메일`)는 입력이 어디서 왔는지를, 결과(`생성됨`·`완료됨`·`실패`)는 DB에 무엇이 쓰였는지를 말한다. `캡처 (생성)` + `실패`는 실제로 있는 조합이다 — 생성 모드로 캡처했지만 만들 것이 없었다. 소스 라벨은 대시보드 패널의 '생성 경로'와 **같은 표**를 쓴다(`app/(app)/messages.ts`).
- **에러 코드를 그대로 보여 주지 않는다.** `NO_TASK_TO_CREATE`는 사용자의 말이 아니다. 앱 알림의 문구("생성할 태스크가 없어요.")와도 다른데, 저쪽은 말을 거는 알림이고 여기는 지나간 기록을 훑는 자리라 웹이 줄곧 써 온 "~습니다"체다.
- **결과 필의 빨강은 글자를 대신하지 않는다.** 필 안에 "실패"라고 이미 적혀 있고 색은 그것을 한 번 더 말한다(키트 3-5).

**마크업 계약** — `<li>`에 `data-log-id` · `data-source` · `data-outcome` · `data-revertable`을 싣는다. `data-due`의 성공을 복제한 것이다: 분류는 마크업에, 문구·색은 자유롭게. `data-revertable`을 따로 두는 이유는 **버튼의 존재로 되돌리기 가능 여부를 유추하지 않기** 위해서다 — [되돌리기]가 나중에 메뉴 안으로 들어가도 검증이 산다.

**딥링크 `?log=<uuid>`** — 앱 알림의 본문 클릭이 여는 자리다(`NTF-4`). 그 항목의 `<li>`에 `aria-current="page"`가 붙고 인디고 테두리가 선다(대시보드에서 열린 행을 짚는 것과 같은 표지). `aria-current`를 링크가 아니라 `<li>`에 다는 것은 이 항목이 **누르는 것이 아니기** 때문이다 — 딥링크로 열린 기록은 "지금 보고 있는 것"이지 "지금 눌린 것"이 아니다.

`?task=`와 같은 태도로, **없거나 남의 것이거나 UUID가 아니면 셋이 같은 자리로 합류**해 목록만 그린다. 여기서는 따로 분기할 것도 없다 — RLS가 남의 로그를 주지 않으므로 어느 경우든 짚이는 항목이 없어진다. 존재 여부가 화면 차이로 새지 않는다.

**고정 문구 둘**

| 자리 | 문구 |
|---|---|
| 요약이 없는 기록 (타임아웃·LLM 오류) | `캡처 내용이 기록되지 않았습니다.` |
| 기록이 하나도 없을 때 | `아직 기록이 없습니다. 앱에서 화면을 캡처하면 여기에 쌓입니다.` |

- 요약이 없는 갈래는 타임아웃과 LLM 오류뿐이다 — 요약은 LLM 출력에서만 나오고, 요약을 위해 한 번 더 부르면 10초 예산을 깬다([`03-Architecture.md`](03-Architecture.md) §설계 결정 17). **"읽지 못했습니다"라고 쓰지 않는다**: 모델이 답한 뒤 해석에 실패한 경우에도 여기로 오는데 그때 모델은 화면을 읽기는 했다. 둘 다에서 참인 문장만 쓴다.

**실시간 반영을 걸지 않는다.** `DASH-5`는 태스크 목록에 걸린 요구사항이고, 히스토리는 지나간 기록을 읽는 자리라 스스로 갱신할 이유가 없다. 이 화면에 `"use client"`가 없다.

## 히스토리 교정 동선 (`L-P1-04`에서 확정)

실패는 **[직접 처리]** 로, 성공은 **[되돌리기]** 로 닫는다(`HIST-2`·`HIST-3`·`HIST-4`). 두 버튼은 기록 한 건의 맨 아래 오른쪽에 서고 **함께 나오는 일이 없다** — 실패 기록은 쓴 것이 없어 늘 되돌릴 수 없고(`NOTHING_TO_REVERT`), 성공 기록은 이어받을 실패가 아니다. 둘 다 없는 항목(이미 되돌린 기록)에는 그 줄 자체가 그려지지 않는다.

**[직접 처리]** — 실패한 기록에만. 목적지는 **소스가 정한다.**

| `source` | 목적지 | 왜 |
|---|---|---|
| `capture_complete` | `/dashboard` | 완료할 것을 사용자가 골라야 한다. 미완료 목록은 대시보드의 기본 화면이라 주소에 실을 것이 없다 |
| 그 밖 | `/dashboard?new=1&from=<logId>` | 새 태스크 패널이 열리고 **서버가** 그 로그의 요약을 제목 칸에 채운다 |

- 🔴 **요약 문장을 URL에 싣지 않는다.** `from=<logId>`만 실린다 — 요약은 캡처 내용이라 주소창·브라우저 히스토리에 남을 자리가 아니다(`AGT-10`의 결). 저장이 거절돼도 `from`이 그대로 따라가 **제목이 빈 칸으로 돌아오지 않는다.**
- 없는·남의 로그와 **요약이 없는 로그**(타임아웃·LLM 오류)는 셋이 같은 자리로 합류한다 — 전부 **빈 폼**이다. `?task=`·`?log=`가 이미 지키는 태도이고, 존재 여부가 화면 차이로 새지 않는다.
- `mail`(P2)은 생성·완료를 스스로 판단해 실패 로그만 보고는 어느 축인지 알 수 없다. **생성 쪽으로 합류시킨다** — 지금 코드는 `mail` 실패 로그를 만들지 않고, 만들게 될 때 다시 본다.
- 📮 **캡처 요약은 문장이지 제목이 아니다.** 실제로 그려 보니 `전체 회의 공지 화면. 참석자 명단과…`처럼 제목 칸에 길게 들어간다. `HIST-2`가 요구하는 것이 그 요약이므로 그대로 두되, 실사용에서 매번 고쳐 쓰게 되면 다시 본다.

**[되돌리기]** — `data-revertable="true"`인 기록에만. `<form>` 안의 `<button>`이다(`<a>`로 만들면 GET에 쓰기가 실린다).

- **확인 단계를 두지 않았다**(사용자 결정 2026-09-24). 생성 되돌리기는 태스크를 지우지만, `TASK_MODIFIED` 가드를 지나온 것만 지워지므로 사라지는 것은 **에이전트가 만들고 사용자가 한 번도 손대지 않은 태스크**뿐이다. 오클릭의 대가가 그만큼 작아 클릭을 하나 더 받지 않는다.
- **성공 안내를 띄우지 않는다**(사용자 결정). [되돌리기]와 관련 태스크 링크가 사라지는 것이 결과다 — 토스트를 두면 z-index 체계가 필요해지고([`08-Design-System.md`](08-Design-System.md)가 "아직 없다"고 적어 둔 것), 화면이 이미 달라졌는데 문장이 한 번 더 말하는 꼴이 된다.
- **두 버튼 모두 2차 버튼이다.** 생성 되돌리기가 삭제를 한다고 빨간 버튼을 주면 **완료 되돌리기가 상대적으로 안전해 보이는데**, 사용자가 누르는 뜻은 둘 다 "에이전트가 한 일을 취소한다" 하나다. 키트의 "채움 인디고는 카드마다 하나"도 지켜진다(행이 카드다).

**거절은 `?error=<사유>`로 돌아오고 문구는 그 기록 안에 선다.**

- 사유 코드를 그대로 보여 주지 않는다. 문장은 **`lib/api/job-logs.ts`의 표 하나**에서 오고(`revertErrorMessage`), `409` 응답의 `message`도 같은 표에서 나온다(`API-5`). 화면이 문장을 복사해 두면 앱과 웹이 언젠가 다른 말을 한다.
- 🔴 **`?log=`이 두 뜻을 겸한다** — 앱 알림의 딥링크 표지(`NTF-4`)이면서 거절된 기록을 짚는 자리다. 화면이 하는 일이 같아서다: 그 항목에 `aria-current="page"`를 달고 인디고 테두리를 세운다. 거절 문구가 **그 항목 안에** 서므로(사용자 결정) 짚는 일과 문구를 붙이는 일이 애초에 한 동작이다. 상단 배너로 하면 기록이 100건까지 쌓이는 화면에서 **어느 것이 거절됐는지**를 말해 주지 못한다.
- 짚히는 항목이 목록에 없으면(그 사이 기록이 사라진 경우) 문구가 **목록 위로** 올라간다. 닿기 어려운 경로지만 문장이 갈 곳을 잃어 조용히 사라지게 두지 않는다.

**`revertable`은 판정을 미리 비춘다.** 버튼은 그것을 따를 뿐이고, 진짜 판정은 되돌리기 트랜잭션 안에서 다시 난다 — 그래서 다른 탭에서 태스크를 고친 직후 눌러도 데이터가 어긋나지 않고 거절 문구를 받는다.

## 설정 (`L-P1-07`에서 확정)

`/settings` — 계정을 확인하고 **스스로 지우는** 자리다(`SET-1`). 앱 셸 안에 서고 사이드바에 화면별 조각을 얹지 않는다(태그 필터 `<nav>`가 0개인 것은 히스토리와 같다).

| 구획 | 내용 |
|---|---|
| 계정 | `이메일` + 주소 한 줄. 읽기 전용이다 |
| 회원 탈퇴 | 안내 한 줄 + **[계정 삭제]** 링크 → `/settings?confirm=delete` |

**탈퇴는 2단계다.**

| 단계 | 주소 | 보이는 것 |
|---|---|---|
| 1 | `/settings` | 무엇이 사라지는지 + [계정 삭제] 링크. 🔴 **`<button>`이 없다** |
| 2 | `/settings?confirm=delete` | 경고 + 계정 이메일 + `이메일` 입력 + [취소]·[영구 삭제] |
| 거절 | `/settings?confirm=delete&error=<code>` | 확인 화면 그대로 + 빨간 문구. **2단계에 머문다** |
| 성공 | `/login` | 쿠키 세션이 지워진 뒤다 |

- 🔑 **`?confirm=delete`는 가드가 아니라 화면 전환이다.** 실제 문턱은 Server Action 안의 이메일 비교 한 줄이고, 그래서 액션을 직접 POST해도 지워지지 않는다. **위조 가능한 URL 값이 삭제의 문턱이 되는 구조를 만들지 않는다** — 이 루프에서 가장 되돌려지기 쉬운 결정이라 `e2e/settings.spec.ts`가 `required`를 벗기고 빈 값을 보내 서버가 막는 것을 확인한다.
- **1단계 → 2단계는 링크(GET)다.** 쓰기가 아니고 화면의 모든 상태가 URL에 있다는 태도 그대로다. "`<a>`로 쓰기를 만들지 않는다"는 금지는 쓰기에 걸린 것이고, 쓰기는 2단계의 `<form>`이 한다.
- **확인은 이메일 재입력이다**(사용자 결정 2026-09-24). 이메일·Google 어느 쪽으로 가입했든 같게 동작한다 — 비밀번호 재입력은 Google 계정에 비밀번호가 없어 한쪽에서 성립하지 않는다. `confirm()`을 쓰지 않으므로 `"use client"`도 열리지 않는다.
- 🔴 **이메일을 본문에도 보인다.** 사이드바에 이미 있지만 저쪽 사본은 240px 안에서 `truncate`라 주소가 길면 잘린다. "그대로 치라"고 요구하는 화면에서 유일한 사본이 잘려 있을 수 없다 — 장식이 아니라 **확인 단계의 전제**다.
- 🔴 **경고를 `Alert`로 그리지 않는다.** `Alert`는 `role="alert"` + 빨강이고 이 저장소에서 뜻이 "폼 실패" 하나로 고정돼 있다. 경고에 쓰면 아무것도 안 했는데 실패한 것처럼 보이고, 거절 문구와 둘이 되어 "무엇이 거절됐는지"를 집는 검증이 흐려진다. 파괴성의 무게는 **danger 버튼 + 이메일 재입력**이 이미 진다. `Notice`(옅은 인디고)도 아니다 — 그쪽은 알리기만 하는 문구의 자리다.
- **[영구 삭제]만 `danger`이고 카드에 인디고 채움 버튼은 없다.** [취소]가 2차 버튼이라 안전한 쪽이 시각적으로 더 무겁다.
- **입력에 `autoComplete="off"`를 준다.** 브라우저가 채워 주면 "그대로 쳐서 확인한다"가 한 번의 클릭이 되어 확인 단계가 사라진다. `app/(auth)/ui.tsx`의 `EmailField`를 재사용하지 않는 이유이기도 하다(그쪽은 `autoComplete="email"`이다).
- **시간대·비밀번호 변경·로그아웃을 두지 않는다.** 시간대는 캡처가 갱신하고([`03-Architecture.md`](03-Architecture.md) §설계 결정 19) 웹 전용 설정 화면을 만들지 않기로 했다 · 비밀번호는 `/reset-password`가 이미 있고 Google 가입 계정에는 뜻이 없다 · 로그아웃은 사이드바에 상시 있어 두 벌이 되면 `getByRole("button", { name: "로그아웃" })`이 둘을 집는다.

**고정 문구**

| 자리 | 문구 |
|---|---|
| 두 단계의 구획 제목 | `회원 탈퇴` |
| 1단계 안내 | `계정과 모든 데이터가 영구히 삭제됩니다. 되돌릴 수 없습니다.` |
| 1단계 링크 | `계정 삭제` |
| 2단계 경고 | `탈퇴하면 태스크, 태그, 작업 기록이 모두 지워집니다. 되돌릴 수 없습니다.` |
| 2단계 확인 요구 | `계속하려면 계정 이메일을 그대로 입력해 주세요.` + 계정 이메일 |
| 2단계 버튼 | `취소` · `영구 삭제` |
| 이메일 불일치 | `이메일이 일치하지 않습니다.` |
| 삭제 실패 | `탈퇴 처리에 실패했습니다. 잠시 후 다시 시도해 주세요.` |

**마크업 계약** — 두 구획이 `aria-labelledby`로 이름 붙은 `<section>`이라 `getByRole("region", { name: "계정" / "회원 탈퇴" })`로 좁힐 수 있다. 📮 **거절 문구를 집을 때 구획으로 먼저 좁힌다** — Next가 라우트 안내용 `role="alert"`를 문서에 하나 더 심어서, 페이지 전체에 `getByRole("alert")`를 걸면 둘이 잡힌다(태스크·태그 패널이 이미 같은 방식으로 좁히고 있다). 입력 라벨은 `이메일`이고 `Field`가 감싼다.

**`?error=` 어휘는 소문자 화면 코드다.** 태그·히스토리가 대문자 API 사유를 쓰는 이유는 그 문장들이 이미 `409` 본문으로 나가는 완성된 한국어이기 때문인데(§태그 관리 패널), 설정에는 API가 없어 대응하는 사유 토큰 자체가 없다. SSOT는 `app/(app)/settings/messages.ts`이고 모르는 코드는 대시보드·인증과 같은 문장으로 합류시킨다.

**거절되면 입력이 비워진다 — 여기서는 그게 맞다.** `?error=`로 도는 동안 타이핑한 값이 날아가는 것은 §태스크 상세 패널·§태그 관리 패널이 이미 감수한 대가인데(살리려면 `useActionState`, 그건 `"use client"`다), 이 화면에서는 **되살리면 안 된다**. 확인의 뜻이 "주소를 그대로 칠 수 있는가"이므로 틀린 뒤 한 글자만 고쳐 다시 누르게 하면 단계가 헐거워진다.

📮 **웹에서 지우면 앱의 토큰은 곧바로 `401`이 된다**(HF-05 — 그 전에는 서버가 서명만 로컬 검증해 잔여 수명 동안 `200`/빈 목록이 왔다). 탈퇴는 `signOut()`을 지나 `/login?signedOut=1`에 도착하므로, 앱 웹뷰에서 탈퇴하면 앱이 그 표시로도 토큰을 버린다 — [`04-API-Contract.md`](04-API-Contract.md) §인증·§앱 로그인, `e2e/settings.spec.ts`가 실증한다.

## 웹에서 놓치기 쉬운 동작

- **정렬과 강조**(`DASH-1`) — 미완료/완료를 나누고 각각 마감 임박 순. 오늘 마감이거나 마감이 지난 미완료 태스크는 강조. **마감일이 없는 태스크는 목록 끝**에 둔다. 확정된 화면은 위 §대시보드 태스크 목록.
- **상세 패널의 6개 항목**(`DASH-3`) — 제목, 설명, 마감일, 상태, **근거**, **생성 경로**. 근거와 생성 경로는 에이전트 판단을 사후 교정하기 위한 것이므로 빠지면 안 된다. (태그는 2026-09-26에 빠졌다 — 위 §태스크 상세 패널.)
- **실시간 반영**(`DASH-5`) — 에이전트가 태스크를 만들거나 완료하면 새로고침 없이 반영된다. 사용자는 캡처 직후 브라우저를 이미 보고 있을 수 있다. 무엇이 반영되고 무엇이 안 되는지는 위 §실시간 반영.
- **딥링크 진입**(`NTF-2`) — 앱 알림에서 넘어올 때 특정 태스크의 상세 패널이 열린 상태로 진입한다. URL에 태스크 ID가 실려야 한다.

## 접근 전제

> 사용자는 앱을 설치하지 않은 상태에서 웹(대시보드)에 접속할 수 없으며, 앱을 설치한 상태에서 대시보드 메뉴를 통해서만 접근이 가능하다(웹 주소 자체가 앱에서 제공된다). 따라서 사용자가 앱이 설치되지 않은 상태로 웹에 접근하는 경우는 상정하지 않는다.

→ **대시보드 안에서는** 앱 설치 유도·미설치 안내를 만들지 않는다. 앱 밖에서 오는 사람을 위한 자리는 `/`의 랜딩 페이지 하나다(결정 기록 11, 2026-09-29 — 이 절은 원래 랜딩 페이지 자체를 금지했다).

- `/policy`(옛 Framer 방침 주소)는 `/privacy`로 영구 이동한다. 방침은 가입 때 동의받는 `/privacy` 하나다.
- macOS 설치 파일은 공증된 dmg를 `public/downloads/Tide-macOS.dmg`에 둔다. 이름에 버전을 넣지 않는다(링크가 릴리스마다 바뀌지 않게). 새 릴리스는 파일을 바꾸고 `DOWNLOADS.mac.note`의 버전을 고친다.
- `proxy.ts`는 `/`와 `/downloads/`를 지나지 않는다 — 로그인과 무관한 정적 응답이다.
- OG 이미지 `app/opengraph-image.png`는 히어로(제목 + 녹화의 포스터)를 1200×630으로 찍은 것이다. 히어로가 바뀌면 다시 찍는다.

# 📱 데스크톱 앱 — 구현 범위 밖

> **Ttabong 저장소 담당이다.** 여기 적는 이유는 `API-3` 응답이 무엇을 담아야 하는지가 이 화면들에서 결정되기 때문이다. 웹은 **알림 표에 들어갈 재료를 전부 응답으로 내주는 것**까지가 제 몫이다.

- **로그인** `P0` — 브라우저에서 웹 로그인한 뒤 딥링크(커스텀 URL 스킴)로 앱에 돌아오는 방식. (`AUTH-3`)
- **권한 온보딩** `P0` — 화면 기록, 접근성 권한 허용을 단계별로 안내한다. (`AUTH-5`)
- **트레이(메뉴바)** — 로그인 계정 확인, 처리 중 표시, 로그아웃, 종료 `P0` · 단축키 안내, 대시보드 바로가기 `P2`. (`CAP-7`, `CAP-9`)
- **캡처 화면** `P0` (`CAP-2`, `CAP-3`, `CAP-5`)
  - OS 기본 캡처로 모드 표시와 앱 연동이 충분히 매끄러우면 OS 기본 캡처를 쓰고, 어려우면 자체 오버레이로 선회한다. (탐색 후 결정)
  - 어느 방식이든 드래그로 영역을 선택하고, OS 기본 캡처와 같은 조작감을 목표로 한다.
  - 현재 모드를 라벨과 색으로 표시한다: `+ 새 태스크` / `✓ 완료`
  - ESC로 취소한다. 선택이 끝나면 캡처 화면은 즉시 사라지고, 트레이 아이콘이 처리 중으로 바뀐다.
- **알림(푸시)** — OS 기본 알림을 사용한다. 웹 푸시는 쓰지 않는다. 형태는 아래와 같다.

| 유형 | 제목 | 본문 | 버튼 | 본문 클릭 |
| --- | --- | --- | --- | --- |
| 실패 | 캡처를 처리하지 못했어요 | 이유 한 줄 (생성할 태스크 없음 / 완료할 태스크를 찾지 못함 / 네트워크 오류) | [대시보드 바로가기] | P0 대시보드 → P1 히스토리 |
| 생성 | 태스크가 추가되었어요 | 제목 , 마감일 (여러 개면 "외 N개") | [대시보드 바로가기] | P0 태스크 상세 → P1 히스토리 |
| 완료 | 태스크가 완료 처리되었어요 | 제목 | [되돌리기] `P2` , [대시보드 바로가기] | P0 태스크 상세 → P1 히스토리 |

- 알림 버튼은 사후 교정 동선이다. 잘못된 완료는 태스크를 목록에서 감춰 놓치기 쉬우므로 완료 알림에만 [되돌리기]를 두고, 잘못된 생성은 대시보드에서 지우면 되므로 바로가기만 둔다.
- 메일 소스(P2)로 생긴 생성, 완료도 같은 형태로 알리고, 본문 앞에 `[메일]`을 붙여 출처를 구분한다. 메일 소스에는 실패 알림이 없다(`AGT-13`).

## 이 표가 웹에 지우는 의무

알림 표의 모든 칸은 `API-3` 응답에서 나와야 한다([`04-API-Contract.md`](04-API-Contract.md) 참조).

| 알림 칸 | 응답 필드 |
|---|---|
| 실패 이유 한 줄 | `data.failure.message` |
| 생성 제목·마감일·"외 N개" | `data.created[]`의 `title`, `dueAt`, 배열 길이 |
| 완료 제목 | `data.completed.title` |
| [대시보드 바로가기] 대상 | `data.created[].id` / `data.completed.id` |
| [되돌리기] 대상 (P2) | `data.jobLogId` |
