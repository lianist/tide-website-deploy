# 02 — 요구사항 (EARS)

> 출처: [`original/functions.md`](original/functions.md) 1~8절 **전량**. 요구사항 문장은 한 글자도 바꾸지 않았다.
> 새로 붙인 것은 **담당** 표시뿐이다. 개발 순서는 [`ROADMAP.md`](ROADMAP.md)가 관리한다.

## 읽는 법

- **표기** — **WHEN** 이벤트가 일어나면 / **WHILE** 특정 상태인 동안 / **IF** 원치 않는 상황이면 / **WHERE** 선택 기능이 켜져 있으면. 키워드가 없는 문장은 항상 지켜야 하는 요구사항이다. "~해야 한다"는 SHALL에 해당한다.
- **주어** — 앱(데스크톱), 대시보드(웹), 에이전트(분석), 시스템(서버 전반), API(앱↔서버 통신).
- **요구사항 ID**(예: `CAP-2`)는 개발자와 에이전트가 요구사항을 지칭하고 테스트 결과를 기록할 때 쓴다. 커밋 메시지·테스트 이름·루프 정의에 그대로 등장한다.
- **담당** — 🌐 **웹**(이 저장소에서 구현) · 📱 **앱**(Ttabong 저장소 담당, 구현 범위 밖) · 🌐📱 **양쪽**(웹이 제 몫을 내고 앱이 소비).

> **이 저장소는 웹만 구현한다.** 📱 항목을 문서에 남기는 이유는 계약(`API-1`)의 상대편을 알아야 웹을 올바르게 만들 수 있기 때문이다. 📱 항목은 [`ROADMAP.md`](ROADMAP.md) 체크리스트에 들어가지 않는다.

## 1. 인증, 온보딩

### P0

- `AUTH-1` 🌐 **WHEN** 사용자가 웹에서 이메일/비밀번호 또는 Google 계정으로 가입하거나 로그인하면, 시스템은 인증 후 대시보드로 이동시켜야 한다.
- `AUTH-2` 🌐 **WHEN** 사용자가 비밀번호 재설정을 요청하면, 시스템은 재설정 메일을 보내야 한다.
- `AUTH-3` 🌐📱 **WHEN** 사용자가 앱에서 로그인을 누르면, 앱은 브라우저에서 웹 로그인을 열고, 인증이 끝나면 딥링크로 앱에 돌아와 같은 계정으로 로그인되어야 한다.
- `AUTH-4` 📱 **WHILE** 앱이 로그인되지 않은 동안, 앱은 단축키 입력 시 캡처 대신 로그인 화면을 띄워야 한다.
- `AUTH-6` 🌐📱 **WHILE** 계정이 개인정보처리방침 동의와 만 14세 이상 확인을 마치지 않은 동안, 시스템은 대시보드 대신 동의 화면을 보여 주고 API를 `403 CONSENT_REQUIRED`로 막아야 한다. 동의하지 않으면 로그아웃시킨다(계정은 지우지 않는다). 방침 시행(2026-09-27) 전에 가입한 계정은 동의한 것으로 본다. (HF-06, 2026-09-27 추가)
- `AUTH-5` 📱 **IF** 화면 기록 또는 접근성 권한이 허용되지 않았으면, 앱은 권한 온보딩을 띄우고, 허용이 확인되면(필요하면 앱 재시작을 안내하고) 다음 단계로 넘어가야 한다.

## 2. 캡처, 트레이 (데스크톱 앱)

> **절 전체가 📱 앱 담당이다.** 웹은 여기서 만들어진 페이로드를 `API-3`으로 받을 뿐이다.

### P0

- `CAP-1` 📱 **WHILE** 로그인되어 있는 동안, 앱은 트레이(메뉴바)에 상주하며 어떤 앱 위에서든 생성 단축키와 완료 단축키를 받아야 한다.
- `CAP-2` 📱 **WHEN** 사용자가 생성 단축키 또는 완료 단축키를 누르면, 앱은 해당 모드(`+ 새 태스크` / `✓ 완료`)가 표시된 캡처 화면을 띄워야 한다.
- `CAP-3` 📱 **WHEN** 사용자가 영역 선택을 마치면, 앱은 캡처 화면을 즉시 닫고 캡처 이미지, 모드, 캡처 시각, 시간대를 캡처 API(`API-3`)로 보내야 한다.
- `CAP-4` 📱 **WHILE** 캡처가 처리되는 동안, 앱은 트레이 아이콘에 처리 중 상태를 표시해야 한다.
- `CAP-5` 📱 **IF** 사용자가 ESC를 누르거나 영역을 선택하지 않고 끝내면, 앱은 아무것도 보내지 않고 캡처 화면을 닫아야 한다.
- `CAP-6` 📱 **IF** 캡처 전송이나 처리가 실패하면(네트워크 오류, 시간 초과 등), 앱은 이를 실패로 처리해야 한다.
- `CAP-7` 📱 트레이 메뉴는 로그인 계정 확인, 로그아웃, 앱 종료를 제공해야 한다.

### P1

- `CAP-8` 📱 앱은 OS 로그인 시 자동으로 실행되어야 한다.

### P2

- `CAP-9` 📱 트레이 메뉴는 단축키 안내와 대시보드 바로가기를 추가로 제공해야 한다.

## 3. 에이전트 처리 (서버)

> **절 전체가 🌐 웹 담당이다.** 제품의 핵심이 여기 있다.

### P0

- `AGT-1` 🌐 **WHEN** 생성 캡처를 받으면, 에이전트는 캡처에서 태스크를 식별해 제목, 설명, 마감일, 태그, 근거(한 문장)를 채워 생성해야 한다. 한 캡처에 태스크가 여러 개면 각각 생성한다. 제목 외에는 필수 필드가 아니다.
- `AGT-2` 🌐 **IF** 생성 캡처에 업무 맥락은 있지만 뚜렷한 할 일이 보이지 않으면, 에이전트는 캡처 요약을 제목으로 하고 마감일은 비운 태스크 하나를 생성해야 한다. 생성 단축키를 누른 것 자체를 생성 의도로 본다.
- `AGT-3` 🌐 **IF** 생성 캡처가 업무와 명백히 무관하면(셀카, 풍경 사진 등), 에이전트는 아무것도 생성하지 않고 '생성할 태스크 없음' 실패로 기록해야 한다. 무관한지 애매하면 `AGT-2`를 따른다.
- `AGT-4` 🌐 에이전트는 '내일', '금요일까지' 같은 상대적 날짜를 캡처 시각과 사용자 시간대 기준의 절대 날짜로 바꿔야 한다. 마감일이 드러나지 않으면 추측하지 않고 비워둔다.
- `AGT-5` 🌐 에이전트는 태스크를 생성할 때 사용자의 기존 태그에 먼저 배정하고, 확실히 새로운 일일 때만 새 태그를 만들어야 한다. 판단이 어려우면 '미분류'에 넣는다. *(해석, 2026-09-29 HF-11: 태그는 **사용자가 속한 조직·활동**(직장·학교·동호회 등) 단위다. "확실히 새로운 일" = 기존 태그 중 그 조직·활동을 가리키는 것이 없는데 소속 단서가 뚜렷한 일, "판단이 어려운 일" = 소속 단서가 없는 개인 볼일. 이전 해석은 분야 태그가 적은 계정에서 모든 일을 '미분류'로 보냈다.)*
- `AGT-6` 🌐 **WHEN** 완료 캡처를 받으면, 에이전트는 사용자의 미완료 태스크 중 캡처와 가장 관련 있는 하나를 골라 완료 처리해야 한다. 후보가 여럿이어도 되묻지 않고 가장 그럴듯한 하나를 고르며, 별도의 신뢰도 지표는 두지 않는다.
- `AGT-7` 🌐 **IF** 완료 캡처와 관련된 미완료 태스크가 하나도 없으면, 에이전트는 아무것도 바꾸지 않고 '완료할 태스크를 찾지 못함' 실패로 기록해야 한다.
- `AGT-8` 🌐 에이전트는 모든 처리 결과를 작업 로그에 남겨야 한다. 실패한 경우에도 캡처 내용을 한 줄로 요약해 남긴다.
- `AGT-9` 🌐 에이전트는 캡처 수신부터 결과 반영까지 10초 안에 처리해야 한다.
- `AGT-10` 🌐 시스템은 캡처 원본을 분석 직후 폐기하고 어디에도 저장하지 않아야 한다. 남는 것은 근거 한 문장과 작업 로그의 요약뿐이다.

### P1

- `AGT-11` 🌐 **IF** 생성하려는 태스크가 기존 미완료 태스크와 같은 일로 판단되면, 에이전트는 새로 만들지 않고 알림으로 이미 있는 태스크임을 알려야 한다.

### P2

- `AGT-12` 🌐 **WHERE** 메일함 연동이 켜져 있으면, **WHEN** 메일이 발신되거나 수신되면, 에이전트는 이를 소스로 삼아 태스크를 생성하거나 완료해야 한다. 생성은 `AGT-1`, `AGT-4`, `AGT-5`, 완료는 `AGT-6`과 같은 기준을 따른다.
- `AGT-13` 🌐 메일에는 모드가 없으므로, 에이전트는 메일마다 생성, 완료, 무시 중 하나를 스스로 판단해야 한다. 메일은 사용자가 의도를 밝힌 입력이 아니므로 `AGT-2`(무조건 생성)는 적용하지 않고, 태스크와 무관한 메일은 알리지 않고 무시한다.

## 4. 알림 (데스크톱 앱)

> 표시는 📱 앱 담당이다. 알림에 들어갈 **내용은 `API-3` 응답이 전부 담아 준다**(`API-3` 참조) — 웹이 지켜야 할 몫은 그 응답의 완결성이다.

### P0

- `NTF-1` 📱 **WHEN** 캡처 처리 결과(생성, 완료, 실패)가 나오면, 앱은 페이지 구성의 알림 표 형태로 OS 알림을 보여줘야 한다. 여러 건이 처리되는 경우에도 각각 알림을 띄워, 사용자가 각 결과에 대하여 개별적으로 조회하거나 되돌릴 수 있도록 한다.
- `NTF-2` 📱 **WHEN** 사용자가 알림의 [대시보드 바로가기]를 누르면, 앱은 브라우저에서 대시보드를 열어야 한다. 관련 태스크가 있으면 그 태스크의 상세 패널을 연 상태로 연다.
- `NTF-3` 📱 **WHEN** 사용자가 알림 본문을 클릭하면, 앱은 `NTF-2`와 같은 화면을 열어야 한다.

### P1

- `NTF-4` 📱 **WHEN** 사용자가 알림 본문을 클릭하면, 앱은 히스토리에서 해당 작업 로그를 열어야 한다. (`NTF-3`을 대체한다.)

### P2

- `NTF-5` 🌐📱 **WHEN** 사용자가 완료 알림의 [되돌리기]를 누르면, 시스템은 해당 태스크를 미완료로 되돌려야 한다. 규칙은 `HIST-3`, `HIST-4`와 같다. 생성 알림에는 [되돌리기]를 두지 않는다.
- `NTF-6` 📱 **WHERE** 메일함 연동이 켜져 있으면, **WHEN** 메일 소스로 태스크가 생성되거나 완료되면, 앱은 같은 형태의 알림을 `[메일]` 출처 표시와 함께 보여줘야 한다.

## 5. 대시보드, 태스크 (웹)

### P0

- `DASH-1` 🌐 대시보드는 태스크를 미완료와 완료로 나눠 각각 마감 임박 순으로 보여주고, 오늘 마감이거나 마감이 지난 미완료 태스크를 강조해야 한다. 마감일이 없는 태스크는 목록 끝에 둔다.
- `DASH-2` 🌐 대시보드는 각 태스크에 태그를 표시해야 하고, **WHEN** 사용자가 태그 필터를 고르면 해당 태그의 태스크만 보여줘야 한다.
- `DASH-3` 🌐 **WHEN** 사용자가 태스크를 클릭하면, 대시보드는 사이드 패널에 제목, 설명, 마감일, 상태, 근거, 생성 경로를 보여줘야 한다. *(원문에는 **태그**도 있었다. 사용자 결정 2026-09-26(HF-03)으로 상세 패널에서 뺐다가, 2026-09-29(HF-10)에 **단일 선택으로 되돌렸다** — 빼고 나니 웹에서 태그를 고칠 곳이 없어 에이전트가 '미분류'로 보낸 태스크를 사용자가 교정할 수 없었다(QA 보고). 결정 기록 3의 '사후 교정'이 태그에도 닿아야 한다.)*
- `DASH-4` 🌐 **WHEN** 사용자가 태스크를 직접 생성, 수정, 삭제하거나 완료, 미완료로 바꾸면, 대시보드는 즉시 저장하고 반영해야 한다.
- `DASH-5` 🌐 **WHEN** 에이전트가 태스크를 생성하거나 완료하면, 대시보드는 새로고침 없이 실시간으로 반영해야 한다.

### P1

- `DASH-6` 🌐 **WHEN** 사용자가 태그 이름을 바꾸거나 두 태그를 병합하면, 시스템은 소속 태스크를 모두 옮기고, 이후 에이전트의 태그 배정(`AGT-5`)도 바뀐 목록을 기준으로 해야 한다.
- `DASH-9` 🌐 대시보드는 태스크를 세 보기로 나눠 보여줘야 한다. '오늘'은 마감이 오늘이거나 이미 지난 미완료 태스크와 마감이 오늘인 완료 태스크(취소선), '전체'는 모든 미완료 태스크, '완료'는 모든 완료 태스크다. 각 보기는 마감 임박 순이고 마감일이 없는 태스크는 끝에 둔다. 태그 필터(`DASH-2`)는 고른 보기를 다시 좁힌다. (`DASH-1`의 미완료/완료 두 구획을 대체한다. 강조 규칙은 그대로다.) *(P0 피드백, 2026-09-25)*
- `DASH-10` 🌐 **WHEN** 사용자가 태스크 행의 완료 표시를 누르면, 대시보드는 그 태스크의 완료·미완료를 바꿔야 한다. 상세 패널의 상태 전환도 같은 표시로 한다. (`DASH-4`의 완료·미완료 전환 수단을 정한다.) *(P0 피드백, 2026-09-25)*
- `DASH-11` 🌐 대시보드는 생성 캡처가 실패한 작업 로그 중 사용자가 아직 처리하지 않은 것을 '확인 필요'로 모아 보여줘야 한다. **WHEN** 사용자가 그 항목의 [직접 처리]로 태스크를 만들거나 [넘기기]를 누르면, 그 항목은 목록에서 빠진다. 남은 건수는 사이드바와 '오늘' 보기 상단에 표시한다. (신뢰도가 낮은 항목이 아니다 — 에이전트는 여전히 되묻지 않는다, 결정 기록 2.) *(P0 피드백, 2026-09-25)*

### P2

- `DASH-7` 🌐 **WHEN** 사용자가 검색어를 입력하면, 대시보드는 제목, 설명, 근거, 태그가 일치하는 태스크를 완료 여부와 관계없이 보여줘야 한다.

### P3

- `DASH-8` 🌐 **WHEN** 사용자가 기간을 골라 보고 초안을 요청하면, 시스템은 그 기간의 태스크 변동사항을 요약한 이메일 초안을 모달로 보여주고 복사할 수 있게 해야 한다.

## 6. 히스토리 (웹)

### P1

- `HIST-1` 🌐 히스토리는 작업 로그를 최신순으로 보여줘야 한다. 각 항목에는 시각, 소스(생성 캡처/완료 캡처/메일), 결과(성공/실패와 이유), 캡처 요약, 관련 태스크가 표시된다.
- `HIST-2` 🌐 **WHEN** 사용자가 실패 항목의 [직접 처리]를 누르면, 대시보드는 생성 실패는 캡처 요약이 채워진 태스크 생성 패널을, 완료 실패는 미완료 태스크 목록을 열어야 한다.
- `HIST-3` 🌐 **WHEN** 사용자가 성공 항목의 [되돌리기]를 누르면, 시스템은 생성은 해당 태스크를 삭제하고, 완료는 해당 태스크를 미완료로 되돌려야 한다.
- `HIST-4` 🌐 **IF** 되돌릴 수 없는 상태면(생성된 태스크를 사용자가 그 사이 직접 수정함, 태스크가 이미 삭제됨, 이미 미완료임), 시스템은 되돌리지 않고 이유를 알려야 한다.

## 7. 설정 (웹)

### P1

- `SET-1` 🌐 **WHEN** 사용자가 회원 탈퇴를 요청하면, 시스템은 확인을 거친 뒤 계정, 태스크, 태그, 작업 로그를 모두 삭제해야 한다.

### P2

- `SET-2` 🌐 **WHEN** 사용자가 메일함 연동을 켜면, 시스템은 Gmail 읽기 권한(발신, 수신 메일)을 요청해야 한다. 연동을 끄면 권한을 해제하고 연동으로 저장된 메일 데이터를 삭제해야 한다.

### P3

- `SET-3` 🌐 **WHERE** 사용자가 알림톡을 켰으면, 시스템은 태스크 생성과 완료를 알림톡으로도 보내야 한다.

## 8. API (앱 ↔ 서버)

> **절 전체가 🌐 웹 담당이다.** 구체 명세는 [`04-API-Contract.md`](04-API-Contract.md)가 들고 있다.

### P0

- `API-1` 🌐 앱은 DB에 직접 접근하지 않고 모든 기능을 서버 API로만 사용해야 한다. 앱과 웹은 API 명세만을 계약으로 삼아 독립적으로 개발한다.
- `API-2` 🌐 API는 태스크와 태그의 전체 CRUD(목록, 조회, 생성, 수정, 삭제, 완료, 미완료 전환)를 제공해야 한다. 현재 앱 화면에서 쓰지 않는 기능도 모두 열어둔다.
- `API-3` 🌐 **WHEN** 앱이 캡처를 보내면, 캡처 API는 처리 결과(생성된 태스크 목록, 완료된 태스크, 또는 실패 이유)와 작업 로그 ID를 응답으로 돌려줘야 한다. 앱은 이 응답만으로 알림을 만들 수 있어야 한다.
- `API-4` 🌐 모든 API 요청은 로그인 토큰으로 인증해야 한다. **IF** 토큰이 없거나 만료되었으면 API는 인증 오류를 반환하고, 앱은 토큰 갱신을 시도한 뒤 실패하면 로그인 화면을 띄워야 한다.
- `API-5` 🌐 비즈니스 로직(에이전트 처리, 되돌리기, 태그 병합 등)은 서버에만 두고, 앱과 웹에 같은 로직을 중복 구현하지 않아야 한다.

### P1

- `API-6` 🌐 API는 작업 로그 조회, 되돌리기, 태그 병합을 제공해야 한다.

### P2

- `API-7` 🌐 메일 소스의 결과는 앱 요청 없이 서버에서 생기므로, API는 앱이 이를 받아 알림을 띄울 수 있는 이벤트 채널(폴링 또는 실시간 구독)을 제공해야 한다.
