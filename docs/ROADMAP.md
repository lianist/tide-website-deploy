> **진입점이 Route Handler가 아니라 페이지인 이유** — 처음엔 Route Handler로 만들었는데, 로그인 Server Action의 `redirect()`가 대상을 서버 안에서 미리 fetch하다 `dochi://`에서 실패해 **로그인 한 번에 코드가 세 번 발급**됐다. 페이지의 `redirect()`로 바꿔 한 번에 끝난다(결정 18).
>
> 함께 바뀐 것: `/login`·`/signup`·`/auth/google`이 `?next=`를 운반한다(`lib/auth/next.ts`) · **웹 로그아웃이 `scope: "local"`** 이 됐다(기본 `global`은 앱 세션까지 끊는다) · `SUPABASE_SECRET_KEY`가 런타임에도 필요해졌다(배포 `L-P0-14`에서 챙길 것).
>
- **수동 확인 2건 완료 (2026-09-23)** — 자동 테스트가 닿지 못하는 구간을 실계정·실브라우저로 확인했다. 판정은 화면이 아니라 **dev 서버 요청 로그**로 했다 — 브라우저가 `dochi://`를 열지 못해 이동을 취소하므로 화면만 보면 아무 일도 없었던 것처럼 보인다(직전 페이지에 머문다).
  - [x] 이메일/비밀번호 — 로그인된 창에서 `/auth/app/start` 진입 → `307`만 찍히고 뒤에 `/login`이 따라오지 않는다(= 목적지가 딥링크다). 코드 발급에 0.3~0.8초
  - [x] **Google** — `/auth/google?next=…` → `/auth/callback?code=…&next=…` → `/auth/app/start` → `307`. **원격 Supabase의 Redirect URL 허용 목록이 쿼리가 실린 콜백 주소를 받는다**는 것을 여기서 처음 실증했다(막히면 조용히 Site URL로 보내므로 자동 테스트가 볼 수 없다)
  - 📮 딥링크 이동이 실패한 뒤 브라우저가 히스토리를 되돌아가면 소모된 Google 콜백 URL을 다시 밟아 `/?error=…bad_oauth_state`로 떨어진다. 스킴 핸들러가 있으면 탭이 그 자리에 머물러 생기지 않는 현상이라 그대로 둔다.
  - 가입 확인 메일로 들어오면 앱이 아니라 대시보드에 도착한다(템플릿이 `next=/dashboard`를 박아 둔 탓, 결정 18의 알려진 한계 ③). 실제로 그렇게 동작하는 것을 확인했다 — 앱에서 로그인을 한 번 더 누르면 바로 넘어간다.

- **알려진 한계 (설계상 받아들인 것)** — 다른 탭·앱에서의 **삭제**와 **태그만 바꾼 저장**은 실시간으로 오지 않는다. 전자는 DELETE에 RLS가 적용되지 않아 듣지 않기로 했고(듣는 순간 남의 태스크 id가 들어온다), 후자는 `tasks` 행이 변하지 않아 신호 자체가 없다. 둘 다 `DASH-5`가 요구하는 에이전트의 생성·완료 밖이다

> **`event: "*"`를 쓰지 않는다.** DELETE에는 RLS가 적용되지 않고 `replica identity`가 기본값이면 `user_id` 필터마저 무시되어 **남의 태스크 id가 브라우저로 흘러든다.** INSERT·UPDATE를 따로 바인딩했고, `replica identity full`로 올리지 않았다(얻는 것은 DELETE 필터링뿐인데 듣지 않는다). 이유는 [`03-Architecture.md`](03-Architecture.md) §설계 결정 21.
>
> **채널 topic에 마운트마다 다른 접미사를 붙인다.** 같은 topic이면 `channel()`이 기존 객체를 돌려주고 `subscribe()`가 join을 보내지 않아, StrictMode의 두 번째 마운트가 **구독 없이 조용히 끝난다** — dev에서만 죽는 모양이다.
>
> **`"use client"`가 0건에서 1건이 됐다.** 대신 그 1건은 데이터를 들지 않는다 — 목록·정렬·태그·시간대 판정은 전부 서버에 그대로 남는다.

**무엇이 이번 작업을 안전하게 만들었나.** P0에서 세워 둔 **마크업 계약**(`05-UI-Spec.md` §마크업 계약)이 전부였다. "분류를 스타일이 아니라 마크업에 적어야 팔레트를 바꿔도 검증이 살아남는다"는 한 줄 덕분에, 69군데의 색과 6종의 글자 크기를 통째로 갈아치우고 대시보드 레이아웃을 2단으로 바꾸는 동안 **테스트를 한 줄도 고치지 않았다.** 101개가 처음부터 끝까지 그대로 통과했다.

**잘못 알 뻔한 것 하나 — `--color-*: initial`은 빌드 게이트가 아니다.** 처음에는 "기본 팔레트를 비우면 `bg-blue-500`이 빌드에서 걸린다"고 적어 두었다. 설계 검토에서 Tailwind v4 소스를 확인해 보니 **모르는 유틸리티는 에러 없이 조용히 버려진다**(에러가 나는 곳은 `@apply` 경로뿐). 남은 `bg-gray-50`은 lint도 build도 통과하면서 스타일만 잃는다. 그래서 ① 리셋을 **모든 화면을 옮긴 뒤 마지막에** 켰고 ② 진짜 그물로 grep 게이트를 문서에 박았다. 이 사실을 몰랐다면 L-DS-01에서 리셋을 켜고 "게이트 통과"라고 적었을 것이고, 어느 화면이 언제 무스타일이 됐는지 추적할 수 없었을 것이다.

**스크린샷만 보고 고칠 뻔한 것 하나.** 로그인 화면의 Google 버튼이 회색으로 보여 2차 버튼 스타일이 틀린 줄 알았다. 계산값을 찍어 보니 `:hover`가 **실제로 걸려 있었다**(마우스가 그 위에 있었다). 육안 검증에서 이상한 것을 봤을 때는 고치기 전에 **계산값을 한 번 묻는다** — 멀쩡한 코드를 고치는 것이 안 고치는 것보다 나쁘다.

**남은 것** — 알려진 흔들림(비밀번호 재설정이 전체 스위트에서만 튕김)은 `L-P1-05` 이후 네 번의 전체 실행에서 **한 번도 나오지 않았다.** 원인을 찾은 것이 아니라 안 나온 것이다. 📮 그대로 둔다.

### 세션 회고 (L4) 덧붙임 — 2026-09-26, P1 후속 6루프 묶음

**어떻게 돌았나** — 사용자 요청(시간 촉박)으로 여섯 루프를 한 번에 돌렸다. 세 갈래 병렬(화면 09→10→12는 본 세션, 서버 11과 이름 13은 워크트리 에이전트) + 루프마다 G1·그 루프 스펙·G4·G5, **G2와 전체 스위트·배포는 합친 뒤 한 번**(사용자 승인). 사람 손이 필요한 대시보드 작업(Vercel·Supabase·Google)은 착수 전에 순서대로 넘겨 개발과 겹쳐 돌렸다.

**1. 반복된 실패가 있었나?** 없다 — 대신 **게이트를 미룬 값이 두 번 청구됐다.** HF-02가 G3 없이 커밋돼 있던 회귀(로그인 전부 정지)와 `L-P1-10`의 경주(저장 뒤 옛 화면)는 둘 다 "전체를 한 번에 돌 때" 드러났다. 루프별 스펙만 돌아서는 안 보이는 종류다 — 전자는 다른 스펙의 공용 도우미가, 후자는 반복 실행이 잡았다. 교훈: **묶음 진행은 통합 실행을 최소 한 번의 반복(`--repeat-each`)과 함께 둔다.** 흔들림을 커밋 단위로 좁힌(09 60/60 → 10 실패) 것이 원인을 한 번에 짚게 했다.

**2. 문서에 없어서 다시 알아낸 것이 있었나?** 하나 — **Vercel의 도메인 "편집" 화면은 옛 주소를 지우거나 넘기는 두 선택지만 준다.** 주소를 **더하려면** Add Domain이다(`L-P1-14` 경위). 워크트리 병렬 테스트에서 `reuseExistingServer`가 남의 dev 서버를 재사용하는 함정은 계획 단계에서 막았다(워크트리마다 포트 + `PLAYWRIGHT_BASE_URL`).

**3. ROADMAP이 실제 상태와 맞나?** 맞췄다. 14/14, P1 게이트 닫힘, P2 열림. 앱 전달 표의 ⬜ 넷은 사람이 넘길 일이다.
