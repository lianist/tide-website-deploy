## 한 줄 정의

**Dochi(도치)** — 화면 일부를 캡처하면 에이전트가 거기서 할 일을 읽어내 **태스크를 자동으로 생성·완료**해 주는 서비스.

핵심 제약: **"나 혼자 도입해서 나 혼자 잘 쓸 수 있어야 한다."** 팀 합의나 동료의 채택 없이 개인이 바로 쓸 수 있어야 한다.

---

## 1. 문제

### 태스크 매니징이 까다롭다

**무엇이?**
- 내가 직접 할 일을 매번 생성해야 한다.
- 상태값을 매번 내가 직접 변경해야 한다.

**왜?**
- 귀찮다.
- 병렬적인 프로젝트가 많다.
- 다른 사람은 안 쓰고 나만 써봤자 공유가 안 된다.
- 나이 많은 선배들이 노션을 사용하지 못한다.
- ~~기존 툴은 개발자 중심이라서 내(마케터)가 쓸 수 없음~~ → **폐기된 진단.** 도구의 개발자 편향이 아니라 *입력 비용* 자체가 문제라고 다시 봤다.

**누가?**
- 저연차 실무자 마케팅 기획. 일단은 기획 파트 마케터.

**언제 가장?**
- 누가 질문을 해서 답변할 때.
- 지금 가장 급한 문제가 무엇인지 파악할 때.

## 2. 솔루션

어디서나 편리하게 스크린샷을 통해 자유롭게 캡처한 사진에서 유저의 태스크 관련 정보를 추출하여, 유저의 태스크를 **자동으로 생성·수정·관리해 주는 웹서비스**.

입력 동선은 단 하나다. **전역 단축키 → 영역 드래그 → 끝.** 확인 팝업도, 폼 입력도 없다.

## 3. 사실과 가정

### 확신할 수 있는 사실

1. 전역 단축키 기반 캡처 호출을 위해서는 **데스크톱 클라이언트(Flutter) 설치가 필수적**이다.
2. macOS 및 Windows 환경에서 캡처 및 전역 단축키 기능을 구현하려면 유저가 직접 **화면 기록 및 접근성을 명시적으로 허용**해야 한다.

### 전제로 삼는 가정

1. 유저는 업무 중 복잡한 태스크 입력 창을 직접 켜는 것보다 **캡처를 더 빠르고 직관적인 기록 수단으로 인지·선호**할 것이다.
2. 비정형 화면(채팅창, 웹페이지, 캘린더 등)의 **일부만 잘라내더라도** 에이전트가 태스크를 충분한 정확도로 식별해낼 것이다.
3. 데스크톱 앱 설치라는 진입 장벽이 존재하더라도, **전역 단축키가 주는 편의성이 설치 번거로움을 우선**할 것이다.
4. 에이전트가 캡처를 분석하고 태스크를 제안하는 과정은 **최대 10초를 넘기지 않을** 것이다. → 요구사항 `AGT-9`로 고정.

### 폐기된 가정 (기록 보존)

- ~~유저는 캡쳐 후 매번 뜨는 태스크 제안 및 승인하는 팝업은 신뢰도를 높여주는 단계로 받아들일 것이다.~~
  → **뒤집혔다.** 승인 팝업은 입력 비용을 되살린다. 에이전트가 먼저 처리하고 사용자는 사후에 교정한다(§5 결정 기록 2·3번). 제품 전체를 관통하는 전환점이므로 삭제하지 않고 남긴다.

## 5. 결정 기록

원본 `functions.md`의 결정 기록 8건을 그대로 옮긴다. 각 결정은 이유와 함께 남긴다 — 나중에 뒤집으려면 이유가 먼저 무너져야 한다.

1. **상태는 미완료/완료 두 가지뿐이다.** 사용자가 상태를 관리하는 순간 입력 비용이 다시 생기기 때문이다.
2. **에이전트는 되묻지 않는다.** 완료 후보가 여럿이어도 하나를 고르고, 신뢰도 지표는 두지 않는다. LLM이 매기는 신뢰도는 자의적이고 재현되지 않으며, 둔다고 동작이 달라지지도 않는다.
3. **교정은 사후에 한다.** 완료 알림의 [되돌리기], 대시보드, 히스토리가 교정 동선이다.
4. **캡처 원본은 저장하지 않는다.** 사내 대화와 고객 정보가 찍히는 서비스이기 때문이다.
5. **웹 푸시는 쓰지 않는다.** 앱이 항상 설치되어 있어 데스크톱 알림과 중복된다.
6. **메일은 캡처와 대등한 소스다** (생성, 완료 모두, 발신, 수신 모두). 노이즈 정교화는 P3 이후로 미룬다.
7. **메일함은 Gmail로 가정**하고, 대회 기간에는 Google 검수 없이 테스트 사용자로 운영한다.
8. **앱 로그인은 브라우저 인증 후 딥링크로 돌아오는 방식**으로 한다.
9. **대시보드는 '보기'로 나눈다 — 오늘 / 전체 / 확인 필요 / 완료** (P0 피드백, 2026-09-25). 한 화면의 미완료·완료 두 구획보다 "지금 무엇을 해야 하나"에 먼저 답한다. **'확인 필요'는 실패한 캡처의 자리이지 신뢰도가 낮은 결과의 자리가 아니다** — 결정 2는 그대로다. 태그 필터는 없애지 않고 보기 아래로 내린다(태그가 '미분류' 하나뿐이면 숨긴다). 완료 전환은 행의 동그라미 하나로 통일한다.
10. **사용자에게 보이는 이름은 Tide다** (P0 피드백, 2026-09-25). 디자인 키트의 이름과 맞춘다. 저장소·DB·딥링크 스킴(`dochi://`)·기존 도메인은 **앱과의 계약이라 그대로 두고**, 새 주소를 하나 더 붙인다. 문서가 제품을 '도치'라고 부르는 것은 내부 코드명으로 남는다.

11. **공개 랜딩 페이지를 둔다** (2026-09-29, 사용자 결정). `/`가 랜딩이다. 앱을 설치하지 않은 사람은 웹에 올 일이 없다는 전제(`05-UI-Spec.md` §접근 전제의 옛 문구)가 무너졌다 — 설치 파일을 받을 곳이 웹밖에 없고, Framer로 만든 임시 페이지(`tide-ai.framer.ai`)가 그 자리를 대신하며 디자인 키트·개인정보처리방침과 따로 놀았다. 랜딩은 **제품이 강제하는 사실만 말한다** — 숫자는 10초(`AGT-9`)·단축키 2개·저장 0장(`AGT-10`)이고, 사용자 수·만족도 같은 숫자는 근거가 생기기 전에는 쓰지 않는다. 화면 명세는 `05-UI-Spec.md` §랜딩 페이지.

> 이후 추가된 설계 결정(캡처 무저장 구현, 10초 예산 처리 방식, Supabase 직접 접근 경계, LLM 프로바이더)은 [`03-Architecture.md`](03-Architecture.md) §설계 결정에 있다.

## 6. 확인 필요

착수 전 결론이 필요한 항목이다. 진행 상황은 [`ROADMAP.md`](ROADMAP.md) §미해결에서 추적한다.

1. **캡처 구현 방식** — OS 기본 캡처 우선 탐색 후, 결과를 공유하고 확정한다. *(앱 담당이나 `API-3` 페이로드 형식에 영향)*
2. **기본 단축키 조합** — 단축키 변경 기능이 없으므로 기본값이 곧 전부다. OS 예약 단축키(macOS의 ⌘⇧3/4/5 등)와 겹치지 않는 조합을 캡처 방식 탐색 때 함께 정한다. *(앱 담당)*
3. **알림톡** — 사업자 채널, 템플릿 사전 검수 등 요구사항과 구현 방법을 먼저 조사한다. (P3)
4. **정확도 목표 수치([N]%)와 비즈니스 모델.**

## 7. 알려진 이슈 (P3 이후 정교화)

- **메일 소스 노이즈** — 공지, 참조, 광고 메일로 불필요한 태스크가 생길 수 있다.
- **메일 소스 비용** — 발신, 수신 메일마다 LLM 호출이 붙는다.
- **태그 파편화** — 에이전트가 같은 태그를 다른 이름으로 만들 수 있다('A 캠페인' / '캠페인 A'). P1의 병합 기능(`DASH-6`)으로 우선 대응한다.
- **완료 오판** — 신뢰도 없이 하나를 고르므로 엉뚱한 태스크가 완료될 수 있다. P0에서는 대시보드에서, P1부터는 히스토리, P2부터는 완료 알림의 [되돌리기]로 교정한다.
- **근거의 직관성** — 향후 근거 기록뿐 아니라 캡처한 이미지를 직접 저장하고 히스토리에서 볼 수 있도록 하여, 판단의 근거를 보다 직관적으로 이해할 수 있게 할 것이다. *(결정 기록 4번과 정면으로 충돌한다. 되살리려면 보존 기간·암호화·사용자 동의를 함께 설계해야 한다.)*

## 8. Non-goals

이번 개발 범위에 **넣지 않는다**고 명시적으로 정한 것들이다.

- **팀 단위 협업 기능**(태스크 할당, 공유 보드)은 포함하지 않는다.
- **자동 일정 배치(스케줄링)는 하지 않는다.** Dochi는 '입력 자동화'에 집중한다.
- **모바일 앱과 웹 푸시는 제외**한다. 알림은 데스크톱 앱에서만 받는다.
- **에이전트는 태스크를 생성하고 완료만 한다.** 제목, 마감일 등의 수정은 사용자만 한다.
- **에이전트는 사용자에게 되묻거나 실행 전 승인을 받지 않는다.**
- **단축키 변경 기능은 두지 않는다.**
