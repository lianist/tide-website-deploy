# 이미 넘긴 것

## 되돌리기 — 2026-09-24 배포 · 2026-09-25 전달 완료

에이전트가 잘못 만들거나 잘못 닫은 것을 물리는 기능입니다. 세 가지가 늘었습니다.

### 1. 작업 기록에 `revertable` 한 칸이 늘었습니다

`GET /api/v1/job-logs`가 주는 각 기록에 불리언 하나가 추가됐습니다.

```jsonc
{
  "id": "uuid",
  "outcome": "created",
  "tasks": [ { "id": "uuid", "title": "교양 발표 PPT 만들기" } ],
  "revertable": true          // ← 새로 생긴 칸
}
```

- **뜻** — 지금 이 기록에 되돌리기를 걸면 성공할지를 서버가 판정한 값입니다. **되돌리기 버튼을 보여 줄지 말지**에 쓰시면 됩니다.
- **참고값입니다.** 목록을 읽은 뒤 사용자가 그 할 일을 고치면 뒤집힐 수 있어서, `true`였는데 실제 호출이 `409`로 떨어질 수 있습니다. 오류가 아니라 정상 흐름이고, 그때는 아래 3번대로 `message`를 그대로 띄워 주세요.
- 앱이 지금 꼭 써야 하는 값은 아닙니다 — 되돌리기 버튼 자체는 다음 단계(P2) 일정입니다.

### 2. 되돌리기 API가 열렸습니다 — `POST /api/v1/job-logs/:id/revert`

**요청 본문이 없습니다.** 무엇을 되돌릴지는 그 기록의 `outcome`이 정합니다.

```jsonc
// 성공 200
{
  "data": {
    "jobLogId": "uuid",
    "reverted": "created",      // created · completed
    "taskIds": [ "uuid" ]       // 실제로 바뀐 할 일. 만든 순서
  }
}
```

- `reverted`가 `created`면 `taskIds`의 할 일이 **지워졌고**, `completed`면 **할 일로 되돌아갔습니다**.
- **두 번 부르면 `409`입니다.** 성공했다면 같은 기록을 다시 되돌릴 것이 없습니다.
- **생성 되돌리기는 전부 아니면 전무입니다.** 캡처 한 장이 할 일 여러 개를 만들 수 있는데, 그중 하나라도 그 뒤에 바뀌었으면 **한 건도 지우지 않고** 거절합니다. 부분 삭제는 일어나지 않습니다.
- 할 일이 지워지면 태그 연결도 함께 사라집니다. 태그 자체는 남습니다.
- 완료를 되돌려도 그 할 일은 기록의 `tasks`에 계속 실립니다 — 무엇을 되돌렸는지 보이게 하려는 것입니다.

**지금 이걸 부르지 않으셔도 됩니다.** 되돌리기 버튼은 P2라, 계약이 서 있다는 통지입니다.

### 3. 에러 코드 두 개가 늘었습니다

| code | HTTP | 뜻 |
|---|---|---|
| `JOB_LOG_NOT_FOUND` | 404 | 작업 기록이 없거나 남의 것 |
| `REVERT_NOT_POSSIBLE` | 409 | 되돌릴 수 없는 상태. **이유는 `message`에 있습니다** |

🔴 **`REVERT_NOT_POSSIBLE`은 코드가 하나뿐이고 사유는 `message`로 갈립니다.** 사유별로 분기하지 마시고 `message`를 그대로 띄워 주세요. 지금은 네 가지이고, **앞으로 늘 수 있습니다.**

- `생성 이후 태스크가 변경되어 되돌릴 수 없습니다.`
- `되돌릴 태스크가 남아 있지 않습니다.`
- `이미 되돌린 작업입니다.`
- `되돌릴 내용이 없는 기록입니다.`

이전에 전달드린 *"모르는 `failure.code`가 오면 `message`를 그대로 띄운다"* 와 같은 태도라, 새로 배우실 것은 없습니다.

없는 기록·남의 기록·UUID 모양이 아닌 `:id`는 **본문까지 똑같은** `404` `JOB_LOG_NOT_FOUND`로 옵니다.

## 히스토리 화면 — 2026-09-24 배포 · 2026-09-25 전달 완료

알림 본문 클릭이 갈 주소가 생겼습니다.

`NTF-4`가 기다리던 자리입니다. 지금까지 알림 본문을 누르면 대시보드나 태스크 상세로 보내셨는데, 이제 **작업 기록 하나를 짚어 여는 주소**가 생겼습니다.

```
https://dochi-six.vercel.app/history?log=<jobLogId>
```

`jobLogId`는 **캡처 응답이 이미 주고 있는 값**입니다(`data.jobLogId`). 새로 받아 올 것이 없고, 알림을 만들 때 이미 손에 들고 있는 값을 그대로 쿼리에 실으시면 됩니다. 세 가지 알림(생성·완료·실패) 모두 같은 주소를 씁니다.

열리면 그 기록이 목록 안에서 테두리로 짚여 보이고, 화면에는 그 한 건만이 아니라 **최근 기록 전체**가 함께 그려집니다. 앞뒤 맥락을 보라는 뜻입니다.

**값이 이상해도 오류 화면이 뜨지 않습니다.** 없는 id, 남의 id, UUID 모양이 아닌 값 — 셋 다 *"짚힌 것 없는 평범한 목록"* 으로 똑같이 열립니다. 알림이 오래된 기록을 가리키고 있어도 사용자에게는 깨진 화면 대신 히스토리가 보입니다.

로그인하지 않은 웹뷰로 열면 로그인 화면으로 보내고, 로그인하면 이 주소로 돌아옵니다 — 대시보드와 같은 동작입니다.

> 기록 한 건에 무엇이 보이는지(시각·출처·결과·요약·완료 근거·관련 태스크)는 `GET /api/v1/job-logs`가 주는 것과 같습니다. 앱이 이 화면을 흉내 낼 일은 없지만, 사용자가 무엇을 보게 되는지 알아 두시면 알림 문구를 정하실 때 도움이 됩니다.

## 태그 합치기 — 2026-09-24 배포 · 2026-09-25 전달 완료

태그 둘을 하나로 합치는 API가 열렸습니다. **새 에러 코드는 없습니다.**

```
POST /api/v1/tags/merge
{ "sourceId": "…", "targetId": "…" }
```

응답은 **남은 태그 한 건**(`targetId` 쪽)이고, 그 `id`와 `createdAt`은 합치기 전과 같습니다 — 새로 만드는 것이 아니라 한쪽을 없애는 동작입니다.

**무엇이 일어나는가**

- `sourceId` 태그가 사라지고, 거기 달려 있던 할 일은 `targetId` 태그를 갖습니다.
- **할 일은 한 건도 사라지지 않습니다.** 태그만 옮겨집니다.
- 둘 다 달려 있던 할 일에는 `targetId` 태그가 **한 번만** 남습니다. 같은 태그가 두 번 붙는 일은 없습니다.

**⚠️ 태그 목록을 캐시하신다면** 합치기 뒤에 다시 받으셔야 합니다. 사라진 태그 id가 손에 남아 있을 수 있고, 그 id로 할 일 목록을 거르면 빈 결과가 옵니다. 할 일의 `tags`와 목록이 어긋나면 그 신호로 보셔도 됩니다.

**거절되는 경우**

| 언제 | 응답 |
|---|---|
| 같은 요청을 두 번 보냄 (출발 태그가 이미 없다) | `404 TAG_NOT_FOUND` |
| 둘 중 하나가 없거나 남의 태그 | `404 TAG_NOT_FOUND` |
| **'미분류'를 `sourceId`로** 지정 | `409 TAG_PROTECTED` |
| 두 id가 같거나, 빠졌거나, UUID 모양이 아님 | `400 VALIDATION_FAILED` |

**'미분류'는 `targetId`로는 쓸 수 있습니다.** 그쪽은 태그가 사라지지 않으니까요 — "잘못 만든 태그를 미분류로 되돌린다"는 정상적인 사용입니다. 막히는 것은 출발점으로 쓰는 경우뿐입니다.

> `TAG_PROTECTED`는 이미 쓰고 계신 코드입니다. 지금까지 '미분류'의 이름 변경·삭제에서만 나왔는데, 이제 **합치기의 출발점**에서도 나옵니다. 코드도 HTTP 상태도 그대로라 기존 분기를 고치실 필요는 없고, 그 자리에서 나올 수 있는 상황이 하나 늘었다는 뜻입니다.

## 중복 감지 — 2026-09-25 전달 완료 · 같은 날 배포

생성 캡처가 **이미 있는 미완료 할 일과 같은 일**이면 새로 만들지 않습니다. 이것만은 지금 쓰고 계신 `POST /api/v1/captures`의 응답이 달라지는 변경이라, 전달이 끝난 뒤에 배포합니다.

**응답에 `duplicates` 한 칸이 늘었습니다.**

```jsonc
"duplicates": [ { "id": "uuid", "title": "보고서 제출하기" } ]   // 이미 있어서 만들지 않은 것
```

- 항목은 **이미 있던** 할 일의 `id`·`title`입니다. 같은 할 일이 두 번 들어 있지 않습니다.
- **언제나 배열로 옵니다.** 겹친 것이 없으면 `[]`, 완료 캡처면 늘 `[]`입니다 — 칸이 있는지가 아니라 길이만 보시면 됩니다.

**결과는 두 모양 중 하나입니다.**

| 캡처의 할 일이 | `outcome` | 함께 오는 것 |
|---|---|---|
| **전부** 이미 있다 | `"failed"` | `failure.code: "DUPLICATE_TASK"`, `created: []`, `duplicates` 1건 이상 |
| **일부만** 이미 있다 | `"created"` | `created`와 `duplicates`가 **둘 다** 찬다 |

**`outcome` 값은 늘지 않았습니다.** 앞서 알려 드린 규칙("모르는 `failure.code`가 오면 `message`를 그대로 띄운다")을 이미 따르고 계시면, 앱을 고치지 않아도 전부 중복인 경우는 실패 알림으로 제대로 뜹니다.

- `message`는 `"이미 있는 태스크예요: 보고서 제출하기"`처럼 **이미 있는 할 일의 제목**을 담고, 둘 이상이면 `"… 외 1건"`이 붙습니다. 그대로 알림 본문으로 쓰시면 됩니다.
- 그 할 일로 가는 [대시보드 바로가기]가 필요하면 `duplicates[0].id`를 쓰십시오. 주소는 생성 알림과 같은 방식입니다.
- **일부만 겹친 경우**, 기존 코드는 `created`만 알림으로 띄우고 겹친 것은 조용히 넘어갑니다. 그래도 틀린 동작은 아닙니다 — 알려 주고 싶으시면 `duplicates`로 알림을 한 건 더 띄우시면 됩니다.
- 비교 대상은 **최근에 만든 미완료 할 일 40건**입니다. 그보다 오래된 할 일과 같은 일은 새로 만들어질 수 있습니다.
