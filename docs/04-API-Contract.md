## 공통 규약 🔒

### 베이스 경로

```
https://dochi-six.vercel.app/api/v1
```

버전을 처음부터 박는다. 앱은 자동 업데이트가 느리므로 구버전 앱이 남는다.

**호스트가 정해졌다**(L-P0-14, 2026-09-23). 앱은 이 주소를 설정 한 곳에만 두고 쓴다 — 도메인이 바뀌면 여기를 고치고 앱에 알린다. `/api/v1` 아래의 경로·요청·응답은 호스트와 무관하게 같다.

**새 주소가 하나 늘었다**(L-P1-14, 2026-09-25) — `https://tide-task.vercel.app/api/v1`. 같은 Vercel 프로젝트의 **별칭**이라 같은 배포가 두 호스트에서 뜬다. 🔴 **옛 주소(`dochi-six`)는 끊지 않는다** — 리디렉트도 걸지 않았다(앱의 POST가 리디렉트를 따라가지 않거나 본문을 잃을 수 있다). 앱이 새 주소로 옮기는 것은 선택이고, 옮기지 않아도 영원히 동작해야 한다. 두 주소 모두 `test:deployed`를 통과한다. 이유는 [`00-Product.md`](00-Product.md) §결정 기록 10.

### 응답 봉투

모든 응답은 두 모양 중 하나다(`03-Architecture.md` §설계 결정 5).

```jsonc
// 성공
{ "data": { ... } }

// 실패
{ "error": { "code": "TASK_NOT_FOUND", "message": "태스크를 찾을 수 없습니다." } }
```

- `code` — 기계가 읽는다. 앱의 분기 조건. SCREAMING_SNAKE_CASE.
- `message` — 사람이 읽는다. 한국어. 알림 본문에 그대로 써도 되는 문장.
- HTTP 상태 코드도 함께 맞춘다(404면 `404` + `TASK_NOT_FOUND`).

### 인증 (`API-4`)

```
Authorization: Bearer <supabase_access_token>
```

- 모든 엔드포인트가 요구한다. 예외 없음.
- 토큰이 없거나 만료 → `401` + `UNAUTHORIZED`. 앱은 리프레시(`POST /auth/app/token`, 아래 §앱 로그인)를 시도하고, 실패하면 로그인 화면을 띄운다.
- **없음·만료·위조의 응답이 전부 같다.** 어느 쪽인지 알려 주면 토큰의 실재 여부를 흘리게 된다. 앱은 `UNAUTHORIZED` 하나만 보고 리프레시로 분기한다.
- 토큰은 유효하나 남의 자원 → `404`. 존재 여부를 흘리지 않기 위해 `403`을 쓰지 않는다. **없는 자원과 남의 자원은 본문까지 동일하다.**
- 📱 **서버는 요청마다 Auth 서버에 토큰을 확인한다**(`getUser`, 2026-09-27 HF-05 — 그 전에는 `getClaims` 로컬 서명 검증). 서명이 유효해도 **사용자가 사라졌거나 세션이 폐기됐으면 `401`**이다. 앱의 로그아웃은 서버에 닿지 않으므로 앱이 버린 액세스 토큰은 남은 수명(기본 1시간)까지 통과한다 — 앱은 로그아웃할 때 저장해 둔 토큰을 직접 지워야 한다. Auth 서버 자체의 실패(5xx·네트워크)는 `401`이 아니라 `500 INTERNAL_ERROR`다(멀쩡한 사용자를 로그아웃시키지 않도록, `/auth/app/token`과 같은 원칙).
- 📱 **회원 탈퇴(`SET-1`) 뒤의 토큰은 즉시 `401`이다.** 하드 삭제가 `auth.sessions`까지 지우므로 리프레시도 `401`이고, 앱은 평소의 401 처리(갱신 → 실패 → 로그인 화면)로 빠져나온다. 로컬 검증 시절에는 `200`/빈 목록이 와서, 탈퇴한 사용자의 앱이 토큰 잔여 수명 동안 **캡처는 실패하는데 로그인 화면으로 돌아오지 않았다**(앱 부서 보고, HF-05). `e2e/settings.spec.ts`가 실증한다.
- 📱🌐 **개인정보처리방침 동의 게이트(`AUTH-6`, HF-06).** `profiles.consented_at`이 null인 계정은 `withAuth`가 `403 CONSENT_REQUIRED`로 막는다. 예외는 `withAuth(handler, { requireConsent: false })`로 연 두 경로뿐 — `GET /api/v1/me`(토큰이 쓸 만한지와 동의 여부를 섞지 않는다)와 `POST /api/v1/web-session`(앱이 웹뷰를 열어 `/consent`에 닿는 유일한 길). 동의 조회는 `getUser`와 **병렬**이라 지연이 늘지 않는다. 기존 계정은 마이그레이션이 동의로 채웠다(사용자 결정 2026-09-27). 웹 화면 쪽 같은 판단은 `requireConsentedUser()`가 한다.
- 🌐 **웹 대시보드는 쿠키 세션을 쓴다.** 두 방식은 공존하며 서로를 대체하지 않는다 — **`/api/v1/*`은 쿠키를 보지 않고**, 웹 화면은 `Authorization` 헤더를 보지 않는다. 앱이 붙는 경로는 언제나 Bearer 쪽이다.

### 공통 에러 코드

| code | HTTP | 의미 |
|---|---|---|
| `UNAUTHORIZED` | 401 | 토큰 없음·만료·무효 |
| `CONSENT_REQUIRED` | 403 | 개인정보처리방침 미동의(HF-06). 남의 자원(404)과 달리 숨길 것이 없어 403이다 |
| `VALIDATION_FAILED` | 400 | 요청 형식 오류 |
| `TASK_NOT_FOUND` / `TAG_NOT_FOUND` | 404 | 대상 없음(또는 남의 것) |
| `JOB_LOG_NOT_FOUND` | 404 | 작업 로그 없음(또는 남의 것) — `TASK_NOT_FOUND`를 재사용하지 않는다 |
| `TAG_NAME_TAKEN` | 409 | 같은 이름의 태그가 이미 있음 (생성·이름 변경) |
| `TAG_PROTECTED` | 409 | '미분류' 태그는 이름 변경·삭제·**병합 출발** 불가 (`AGT-5`의 전제) |
| `REVERT_NOT_POSSIBLE` | 409 | 되돌릴 수 없는 상태 (`HIST-4`) — 사유는 `message`에 |
| `NO_TASK_TO_CREATE` | 200 | 생성할 태스크 없음 (`AGT-3`) — 실패지만 **요청 자체는 성공**이므로 `data.failure`로 전달 |
| `NO_TASK_TO_COMPLETE` | 200 | 완료할 태스크를 찾지 못함 (`AGT-7`) — 위와 같음 |
| `DUPLICATE_TASK` | 200 | 캡처의 할 일이 **전부** 이미 있는 미완료 태스크와 같음 (`AGT-11`) — 위와 같음. `message`에 기존 태스크 제목이 실린다 |
| `AGENT_TIMEOUT` | 504 | 10초 예산 초과 (`AGT-9`) |
| `INTERNAL_ERROR` | 500 | 그 밖 |

> **`AGT-3`/`AGT-7`/`AGT-11`은 `error`가 아니라 `data`로 돌려준다.** 에이전트가 정상 동작한 결과이고, 앱은 이것으로 실패 알림을 만들어야 하므로 `jobLogId`가 함께 필요하기 때문이다.

### 명명

- 요청·응답 JSON은 **카멜케이스**(`dueAt`, `jobLogId`). DB는 스네이크케이스이며 경계에서 한 번 변환한다.
- 시각은 전부 **ISO 8601 UTC**(`2026-09-20T05:30:00Z`). 응답은 DB 표기 그대로라 `2026-09-20T05:30:00.123456+00:00`처럼 **`+00:00`과 소수 초로 올 수 있다** — 표준 ISO 파서로 읽으면 같은 시각이다. 요청의 시각은 오프셋이 붙은 어떤 ISO 문자열이든 받아 UTC로 정규화한다.

## 엔드포인트 (스텁 — 구현하며 채운다)

### 인증 — L-P0-03·04·05

| 메서드 | 경로 | 요구사항 | 비고 |
|---|---|---|---|
| — | 웹 페이지 `/login`, `/signup`, `/reset-password`, `/reset-password/update`, `/dashboard` | `AUTH-1`, `AUTH-2` | ✅ 브라우저 흐름(쿠키 세션). API 아님 |
| `GET` | `/auth/google` | `AUTH-1` | ✅ Google 동의 화면으로 리다이렉트 |
| `GET` | `/auth/callback` | `AUTH-1`, `AUTH-2` | ✅ 바깥에서 돌아온 사용자의 세션을 세운다 (아래) |
| `GET` | `/auth/app/start` | `AUTH-3` | ✅ 앱이 브라우저로 여는 진입점. 인증 후 일회용 코드를 딥링크로 (아래 §앱 로그인) |
| `POST` | `/auth/app/token` | `AUTH-3` | ✅ 코드 → 세션 교환 · 세션 갱신. **Bearer 없이** 부른다 (아래 §앱 로그인) |
| `GET` | `/api/v1/me` | `API-4` | ✅ 토큰 검증 + 계정 확인 (`CAP-7`의 "로그인 계정 확인") |
| `POST` | `/api/v1/web-session` | `AUTH-3` | ✅ 앱 세션을 앱 안 웹뷰로 잇는 일회용 로그인 주소 (아래 §앱 로그인) · 2026-09-25 핫픽스 |

**`GET /auth/callback`** — 들어오는 길이 둘이고 둘 다 "세션을 세우고 `next`로 보낸다"로 끝난다.

| 쿼리 | 어디서 오나 | 처리 |
|---|---|---|
| `code` | Google OAuth | `exchangeCodeForSession` |
| `token_hash` + `type`(`signup`\|`recovery`) | 가입 확인·비밀번호 재설정 메일 | `verifyOtp` |

`next`는 **`/`로 시작하는 내부 경로만** 허용한다(`//`로 시작하는 값은 바깥 도메인이므로 거부). 실패하면 `/login?error=link_expired`. `/login`·`/signup`·`/auth/google`도 같은 규칙의 `?next=`를 받아 끝까지 운반한다. 앱 딥링크 스킴은 `next`로 열지 않는다 — `next`는 언제나 `/auth/app/start`라는 내부 경로다.

> 메일 링크는 `code`가 아니라 **`token_hash`**를 싣는다. `code` 방식은 링크를 연 브라우저에 검증용 쿠키가 있어야 해서, 컴퓨터에서 가입하고 폰에서 메일을 열면 깨진다. 메일 템플릿이 이 형식으로 링크를 만든다([`03-Architecture.md`](03-Architecture.md) §설계 결정 12).

```jsonc
// GET /api/v1/me — DB를 치지 않는다. 답이 전부 검증된 토큰 안에 있다.
{ "data": { "id": "uuid", "email": "someone@example.com" } }
```

#### 앱 로그인 (`AUTH-3`) — L-P0-04 📱

앱은 **브라우저와 다른, 자기만의 세션**을 받는다. 브라우저 세션을 나눠 쓰면 리프레시 토큰 회전 때문에 둘이 번갈아 로그아웃된다([`03-Architecture.md`](03-Architecture.md) §설계 결정 18).

```
1. 앱 → 브라우저 열기   GET /auth/app/start?redirect_uri=dochi://auth/callback&state=<앱이 만든 임의값>
2. (로그인 전이면)      /login?next=… → 이메일/비밀번호 또는 Google → 다시 /auth/app/start
3. 브라우저 → 앱        dochi://auth/callback?code=<일회용 코드>&state=<1의 값 그대로>
4. 앱 → 서버           POST /auth/app/token  { "grantType": "code", "code": "<3의 code>" }
                       ← { "data": { accessToken, refreshToken, expiresAt, user } }
```

- **스킴은 `dochi://auth/callback` 하나뿐이다.** `redirect_uri`가 이 문자열과 **정확히** 같지 않으면(뒤에 경로·쿼리를 덧붙인 것 포함) 오류 화면을 보여 주고 어디로도 보내지 않는다. 앱은 이 스킴을 OS에 등록해야 한다.
- **`state`** — 앱이 만든 값을 그대로 돌려준다. 앱은 3에서 받은 `state`가 자기가 보낸 것과 다르면 버린다(다른 곳에서 시작된 로그인을 받지 않기 위해). 선택 항목이지만 보내는 것을 권한다.
- **코드는 일회용이고 1시간 뒤 만료된다.** 받으면 바로 교환한다. 새 코드가 발급되면 이전 코드는 무효가 된다.
- 3에서 `code` 대신 **`error=server_error`** 가 오면 서버가 코드를 만들지 못한 것이다. 로그인을 다시 시작하게 한다.
- 브라우저가 이미 로그인돼 있으면 1에서 곧바로 3으로 간다(그 계정으로). 가입 확인 메일의 링크는 대시보드로 가므로, 메일로 가입한 직후에는 앱에서 로그인을 한 번 더 누르면 된다.

**`POST /auth/app/token`** — `/api/v1` 밖에 있고 **`Authorization` 헤더를 보지 않는다**(토큰이 없거나 만료된 앱이 부르는 곳이라). 봉투는 같다.

| `grantType` | 함께 보내는 것 | 하는 일 |
|---|---|---|
| `code` | `code` | 딥링크로 받은 코드를 세션으로 바꾼다 |
| `refreshToken` | `refreshToken` | 세션을 갱신한다. `/api/v1`이 `401`을 주면 여기로 온다 |

```jsonc
// 두 갈래 모두 같은 모양
{
  "data": {
    "accessToken": "eyJ…",                  // 이후 Authorization: Bearer 에 싣는다
    "refreshToken": "…",                     // 갱신할 때마다 **새 값으로 바뀐다** — 받은 즉시 교체 저장
    "expiresAt": "2026-09-23T06:00:00.000Z", // accessToken 만료 시각
    "user": { "id": "uuid", "email": "someone@example.com" }
  }
}
```

| 상황 | 응답 |
|---|---|
| 잘못됐거나 만료됐거나 이미 쓴 코드·리프레시 토큰 | `401 UNAUTHORIZED` — 앱은 로그인 화면을 띄운다 |
| `grantType`이 둘 중 하나가 아님 · 짝이 되는 값이 없음 · JSON이 아님 | `400 VALIDATION_FAILED` |
| 인증 서버 자체의 실패 | `500 INTERNAL_ERROR` — 로그아웃시키지 말고 나중에 다시 시도 |

- **리프레시 토큰은 한 번 쓰면 바뀐다**(회전). 옛 값을 다시 쓰면(10초 유예 뒤) 세션 전체가 폐기되므로, 갱신 응답의 `refreshToken`으로 **반드시** 덮어쓴다. 갱신을 동시에 두 번 보내지 않는다.
- **로그아웃은 각자 한다.** 웹에서 로그아웃해도 앱 세션은 살아 있고, 앱은 로그아웃할 때 저장한 토큰을 지우기만 하면 된다(서버에 알릴 경로는 아직 없다 — 이미 발급된 액세스 토큰은 어차피 만료까지 통과한다, §인증).
- **웹 로그아웃 신호 — `/login?signedOut=1`** (HF-05). 서버의 앱 세션은 웹 로그아웃으로 끊기지 않지만(`scope: "local"`), **사용자가 직접 누른 로그아웃**(과 탈퇴)은 `/login?signedOut=1`에 도착한다. 세션 만료로 오는 `/login`(`requireUser()`)에는 붙지 않는다. 앱 웹뷰가 이 표시를 보면 앱도 자기 토큰을 버린다 — 보이는 로그아웃 버튼은 하나인데 양쪽이 같이 로그아웃된다. 이 도착에는 `web-session`을 부르지 않는다(부르면 방금 로그아웃한 계정으로 되살아난다).
- ⚠️ PKCE는 아직 없다. 스킴 하이재킹에 대한 방어가 코드의 일회성·짧은 수명뿐이다(§설계 결정 18 알려진 한계).

**`POST /api/v1/web-session`** — 앱 세션을 **앱 안 대시보드 웹뷰**로 잇는다(2026-09-25 핫픽스). 웹뷰는 쿠키 세션이 따로라 잇지 않으면 웹 로그인을 한 번 더 요구하고, macOS 웹뷰에선 그 Google 로그인이 성립하지 않는다(§설계 결정 18).

```jsonc
// 요청 — Bearer 필수. 본문은 선택: 로그인 뒤 갈 내부 경로(기본 /dashboard, 규칙은 위 `next`와 같다)
{ "next": "/history?log=<jobLogId>" }

// 응답 — 웹뷰가 그대로 연다. 기존 /auth/callback의 token_hash 분기가 쿠키 세션을 세우고 next로 보낸다
{ "data": { "url": "https://dochi-six.vercel.app/auth/callback?token_hash=…&type=magiclink&next=%2Fdashboard" } }
```

- 주소는 **일회용·1시간**. 두 번째로 열면 `/login?error=link_expired`.
- 딥링크 코드와 같은 열쇠(magiclink)라 **새로 발급하면 이전 코드가 무효**다 — 앱은 `POST /auth/app/token` 교환을 **끝낸 뒤** 부른다. 연달아 부르는 것은 막히지 않는다(실측).
- 실패는 `401 UNAUTHORIZED`(Bearer) · `500 INTERNAL_ERROR`(발급 실패 — 웹뷰는 로그인 화면에 둔다).

### 태스크 · 태그 (`API-2`) — L-P0-06

> **앱이 지금 안 쓰는 것도 전부 연다**(`API-2` 원문). 앱 화면이 나중에 늘어날 때 서버를 다시 건드리지 않기 위해서다.

| 메서드 | 경로 | 비고 |
|---|---|---|
| `GET` | `/api/v1/tasks` | ✅ 목록. `status`·`tagId` 쿼리 필터. 정렬은 `DASH-1` 규칙 |
| `POST` | `/api/v1/tasks` | ✅ 생성 (`source`는 항상 `manual`) |
| `GET` | `/api/v1/tasks/:id` | ✅ 조회 |
| `PATCH` | `/api/v1/tasks/:id` | ✅ 수정 (상태 전환 포함) |
| `DELETE` | `/api/v1/tasks/:id` | ✅ 삭제 |
| `GET` | `/api/v1/tags` | ✅ 목록 (이름순) |
| `POST` | `/api/v1/tags` | ✅ 생성 |
| `PATCH` | `/api/v1/tags/:id` | ✅ 이름 변경. **병합**은 `API-6`(P1) |
| `DELETE` | `/api/v1/tags/:id` | ✅ 삭제 |

모든 `:id`는 UUID 꼴이 아니어도 `400`이 아니라 **`404`로 합류한다.** 앱은 자기가 받은 id만 쓰므로 실질적으로 "없는 자원"이고, 분기를 하나 줄이는 편이 낫다. 남의 자원은 읽기든 쓰기든 **없는 자원과 본문까지 같은 404**다.

#### 태스크

한 건의 표현. 목록(배열)·조회·생성·수정이 모두 같은 모양을 쓴다.

```jsonc
{
  "data": {
    "id": "uuid",
    "title": "제안서 초안 보내기",
    "description": "...|null",
    "dueAt": "2026-09-22T09:00:00Z|null",   // AGT-4 — 드러나지 않으면 null
    "dueHasTime": true,                      // 마감에 시각이 있는가. 날짜만 있는 마감이면 false (아래)
    "status": "todo|done",                   // 두 값뿐 (결정 기록 1)
    "rationale": "...|null",                 // 에이전트가 왜 이렇게 판단했는지 한 문장
    "source": "capture_create|mail|manual",  // 생성 경로. 완료 캡처는 태스크를 만들지 않는다
    "jobLogId": "uuid|null",
    "tags": [ { "id": "uuid", "name": "업무" } ],   // 이름순. 없으면 []
    "createdAt": "2026-09-20T05:30:00Z",
    "updatedAt": "2026-09-20T05:30:00Z"
  }
}
```

- **소유자(`userId`)는 싣지 않는다.** 자기 것만 보이므로 알려 주는 것이 없다.
- **날짜만 있는 마감**('9/21까지') — `dueAt`은 사용자 시간대 기준 **그날 23:59:59**, `dueHasTime`은 `false`다. 화면·알림은 `dueHasTime`이 `false`면 시각을 숨기고 날짜만 보인다. 정렬과 "마감 지남" 판정은 `dueAt` 하나로 그대로 맞는다. `dueAt`이 `null`이면 `dueHasTime`은 언제나 `false`. 이유는 [`03-Architecture.md`](03-Architecture.md) §설계 결정 14.

**`GET /api/v1/tasks`** — 쿼리는 둘 다 선택.

| 쿼리 | 값 | 비고 |
|---|---|---|
| `status` | `todo` \| `done` | 그 밖의 값(빈 값 포함)은 `400` |
| `tagId` | 태그 UUID | 그 태그가 달린 태스크만. **실린 `tags`는 걸러지지 않고 전부 온다.** 남의 태그·없는 태그면 빈 배열. UUID 꼴이 아니면 `400` |

정렬(`DASH-1`): 미완료 → 완료, 각각 `dueAt` 오름차순, **`dueAt`이 없는 것은 끝**, 같으면 먼저 만든 것이 앞. 페이지네이션은 없다.

**`POST /api/v1/tasks`** — 사용자가 직접 만든다(`DASH-4`). 응답은 만든 태스크 한 건.

```jsonc
{
  "title": "제안서 보내기",          // 필수. 앞뒤 공백을 걷고 비면 400
  "description": "초안 v2",         // 선택. 빈 문자열은 null로
  "dueAt": "2026-09-25T18:00:00+09:00", // 선택. ISO 8601, UTC로 정규화
  "dueHasTime": true,                // 선택. dueAt과 함께만. 생략하면 dueAt이 있을 때 true
  "tagIds": ["uuid"]                 // 선택. 중복은 한 번으로
}
```

- `status`는 받지 않는다 — 새 태스크는 언제나 `todo`. `source`는 `manual`, `rationale`·`jobLogId`는 `null`.
- `tagIds`에 없거나 남의 태그가 하나라도 있으면 `400 VALIDATION_FAILED`이고 **태스크도 만들어지지 않는다**(태스크와 태그 연결이 한 트랜잭션).

**`PATCH /api/v1/tasks/:id`** — 보낸 키만 바꾼다. 응답은 바뀐 태스크 한 건.

| 키 | 값 | 비고 |
|---|---|---|
| `title` | 문자열 | 비면 400 |
| `description` | 문자열 \| `null` | `null`이나 빈 문자열이면 비운다 |
| `dueAt` | ISO 8601 \| `null` | `null`이면 비운다(`dueHasTime`도 `false`가 된다) |
| `dueHasTime` | boolean | **`dueAt`과 함께만** 보낸다. 생략하면 `true` — 날짜만 있는 마감은 그날 23:59:59를 `dueAt`에 싣고 `false`를 보낸다. 혼자 오거나 `dueAt: null`과 `true`가 함께 오면 `400` |
| `status` | `todo` \| `done` | 완료·미완료 전환 |
| `tagIds` | UUID 배열 | **통째로 교체**한다. `[]`이면 태그를 전부 뗀다 |

- 바꿀 키가 하나도 없으면 `400`. `rationale`·`source`·`jobLogId`는 **에이전트 판단의 기록이라 받지 않고 조용히 무시한다.**
- 필드와 태그는 두 단계로 쓰인다. 드물게 둘 사이에서 실패하면 `500`이 나가고 필드만 바뀌어 있을 수 있다 — **같은 PATCH를 다시 보내면 된다**(멱등).

**`DELETE /api/v1/tasks/:id`** → `{ "data": { "id": "uuid" } }`. 달려 있던 태그는 남는다.

#### 태그

```jsonc
{ "data": { "id": "uuid", "name": "업무", "createdAt": "2026-09-20T05:30:00Z" } }
```

- `POST /api/v1/tags` · `PATCH /api/v1/tags/:id` — 본문 `{ "name": "업무" }`. 앞뒤 공백을 걷고 비면 `400`. 같은 이름이 이미 있으면 `409 TAG_NAME_TAKEN`(이름은 사용자마다 유일하다). 응답은 태그 한 건.
- `DELETE /api/v1/tags/:id` → `{ "data": { "id": "uuid" } }`. **태스크는 남고** 그 태그만 떨어진다.
- **'미분류'** — 가입할 때 자동으로 생기고, 에이전트가 태그를 정하기 어려울 때 쓴다(`AGT-5`). 이름 변경·삭제는 `409 TAG_PROTECTED`. 다른 태그를 '미분류'라는 이름으로 만들거나 바꾸면 `TAG_NAME_TAKEN`이다.
- **태그 병합**(`DASH-6`)은 `POST /api/v1/tags/merge`이고 §작업 로그·되돌리기·태그 병합에 있다 — `API-6`이 묶는 세 엔드포인트 중 하나라서다. '미분류'는 병합의 **출발**로 쓸 수 없고 **도착**으로는 쓸 수 있다.

### 캡처 (`API-3`) — L-P0-10 · 중복 감지 L-P1-08

| 메서드 | 경로 | 비고 |
|---|---|---|
| `POST` | `/api/v1/captures` | ✅ 캡처 한 장 → 태스크 생성 또는 완료. 처리 결과와 작업 로그 id를 한 응답에 담는다 |

```
POST /api/v1/captures
Content-Type: multipart/form-data
```

| 필드 | 타입 | 필수 | 비고 |
|---|---|---|---|
| `image` | file | ✅ | **저장하지 않는다**(`AGT-10`). 메모리에서 처리 후 폐기. PNG·JPEG·WebP, **4MB 이하** (아래) |
| `mode` | `create` \| `complete` | ✅ | 사용자가 누른 단축키 (`CAP-2`) |
| `capturedAt` | ISO 8601 | ✅ | 상대 날짜 환산 기준 (`AGT-4`). 오프셋이 붙은 어떤 ISO 문자열이든 받는다 |
| `timezone` | IANA (`Asia/Seoul`) | ✅ | 같음. **계정의 기본 시간대도 이 값으로 갱신된다** (아래) |

- **`timezone`은 그 캡처의 환산 기준인 동시에 계정의 기본 시간대(`profiles.timezone`)를 갱신한다.** 대시보드의 "오늘 마감" 판정과 날짜 표시가 이 값을 쓰고(서버가 그린다 — 배포 환경은 UTC다), 보낼 앱이 없는 메일 소스(P2)도 이 값을 쓴다. 갱신은 에이전트 호출과 **병렬로** 돌아 10초 예산에 왕복을 더하지 않으며, **실패해도 캡처 결과를 바꾸지 않는다**(응답은 그대로 나가고, 타임아웃·실패 응답이어도 갱신은 남는다).
- 📱 **`image` 파트에 Content-Type(`image/png`·`image/jpeg`·`image/webp`)을 반드시 붙인다.** 서버는 파트의 타입을 그대로 믿는다. Flutter `http`의 `MultipartFile`은 지정하지 않으면 `application/octet-stream`을 보내 `400`이 된다.
- 📱 **긴 변 2048px 이하로 줄여 보내기를 권한다.** 모델이 어차피 그 크기로 줄여서 읽으므로 잃는 것이 없고, 4MB 상한(배포 플랫폼의 요청 본문 한도 4.5MB 아래)에 걸리지 않는다.
- 네 칸 중 하나라도 빠지거나 틀리면(multipart가 아님·빈 파일·지원하지 않는 타입·4MB 초과·모르는 `mode`·해석할 수 없는 시각·모르는 시간대) `400 VALIDATION_FAILED`이고 **에이전트를 부르지 않는다** — 작업 로그도 남지 않는다.

응답 — **앱은 이 하나로 알림을 전부 구성할 수 있어야 한다**(`API-3`, `NTF-1`):

```jsonc
{
  "data": {
    "jobLogId": "uuid",
    "outcome": "created" | "completed" | "failed",
    "created": [ { "id": "uuid", "title": "...", "dueAt": "...|null", "dueHasTime": false, "tags": ["..."], "rationale": "..." } ],
    "completed": { "id": "uuid", "title": "..." } | null,
    "duplicates": [ { "id": "uuid", "title": "..." } ],   // 항상 있다. 없으면 []
    "failure": { "code": "NO_TASK_TO_CREATE", "message": "생성할 태스크가 없어요." } | null
  }
}
```

- 한 캡처에서 태스크가 여러 개 나오면 `created` 배열에 전부 담는다(`AGT-1`). 앱은 건마다 알림을 띄운다(`NTF-1`).
- `mode: create`면 `completed`는 항상 `null`, 반대도 마찬가지다.
- `created[].tags`는 태그 **이름** 배열이다(알림 본문용). 비어 있지 않다 — 정하지 못하면 `["미분류"]`.
- **`duplicates`는 이미 있는 미완료 태스크와 같은 일이라 만들지 않은 것**이다(`AGT-11`, L-P1-08). 항목은 그 **기존** 태스크의 `id`·`title`이고, id가 겹치지 않는다. **언제나 배열로 온다** — 앱이 칸의 유무가 아니라 길이만 보게. `mode: complete`면 늘 `[]`.
  - 전부 중복 → `outcome: failed` + `DUPLICATE_TASK`. `message`는 `"이미 있는 태스크예요: {첫 제목}"`, 둘 이상이면 뒤에 `" 외 N건"`.
  - 일부 중복 → `outcome: created`이고 `created`·`duplicates`가 **둘 다** 찬다. `outcome` 열거형은 늘지 않았다.
  - 비교 대상은 **최근에 만든 미완료 태스크 40건**이다. 판정은 에이전트가 같은 호출 안에서 한다(`03-Architecture.md` §설계 결정 27).
  - 작업 로그의 `rationale`은 여전히 완료 로그에서만 찬다 — 무엇과 겹쳤는지는 이 응답에만 있다.

**결과 한눈에** — 앱의 분기는 HTTP 상태와 `outcome` 두 개로 끝난다.

| HTTP | 모양 | 뜻 | 반영된 것 |
|---|---|---|---|
| `200` | `data.outcome: created` | 태스크 1개 이상 생성 | `created[]` 전부 |
| `200` | `data.outcome: completed` | 태스크 하나를 `done`으로 | `completed` |
| `200` | `data.outcome: failed` + `failure.code` `NO_TASK_TO_CREATE`/`NO_TASK_TO_COMPLETE` | 에이전트가 할 일을 찾지 못함 | 없음 |
| `200` | `data.outcome: failed` + `failure.code` `DUPLICATE_TASK` | 할 일이 전부 이미 있음 (`AGT-11`) | 없음 — 기존 것은 `duplicates` |
| `400` | `VALIDATION_FAILED` | 요청 형식 오류 | 없음 (로그도 없음) |
| `401` | `UNAUTHORIZED` | 토큰 문제 | 없음 |
| `504` | `AGENT_TIMEOUT` | 10초 예산 초과 (`AGT-9`) | **없음이 보장된다** — 시간 제한은 반영 전 단계(모델 분석)에만 걸린다 |
| `500` | `INTERNAL_ERROR` | 그 밖 | 드물게 생성의 일부가 남을 수 있다 |

- 모든 결과가 작업 로그를 남긴다(`AGT-8`) — `400`·`401`만 예외. 다만 `504`·`500`은 실패 봉투라 `jobLogId`를 싣지 않는다(되돌릴 것이 없다).
- 10초는 서버가 요청을 받은 순간부터 잰다. 모델 분석이 끝난 뒤 저장에 걸리는 시간(≈ 1초 미만)만큼은 넘길 수 있고, 그때도 결과는 정상 `200`이다. 📱 앱의 HTTP 타임아웃은 여유를 두어 **15초 이상**으로 잡는다.

### 작업 로그 · 되돌리기 · 태그 병합 (`API-6`) — L-P1-01 · L-P1-02 · L-P1-05

| 메서드 | 경로 | 요구사항 | 비고 |
|---|---|---|---|
| `GET` | `/api/v1/job-logs` | `HIST-1` | ✅ 작업 로그 최신 100건. 쿼리 없음 |
| `POST` | `/api/v1/job-logs/:id/revert` | `HIST-3`, `HIST-4`, `NTF-5` | ✅ 로그 하나를 되돌린다. 요청 본문 없음 |
| `POST` | `/api/v1/tags/merge` | `DASH-6` | ✅ 태그 둘을 하나로 합친다 |

**`GET /api/v1/job-logs`** — 에이전트가 입력 한 건을 처리한 기록(`AGT-8`)을 최신순으로 돌려준다.

```jsonc
{
  "data": [
    {
      "id": "uuid",
      "createdAt": "2026-09-24T03:00:00Z",
      "source": "capture_create" | "capture_complete" | "mail",
      "outcome": "created" | "completed" | "failed",
      "failureReason": "NO_TASK_TO_CREATE" | null,
      "captureSummary": "노트 앱에 적힌 할 일 두 가지." | null,
      "rationale": "캡처의 '완료' 표시가 이 태스크의 제목과 같다." | null,
      "handledAt": "2026-09-25T02:10:00Z" | null,
      "tasks": [ { "id": "uuid", "title": "..." } ],
      "revertable": true
    }
  ]
}
```

- **최신 100건 고정이다.** 쿼리도 페이지네이션도 없다. 커서는 나중에 **더하는 변경**으로 열 수 있다.
- `tasks[]`는 **그 로그가 만들었거나 닫은** 태스크다. 생성 로그면 만든 것 전부(`AGT-1`), 완료 로그면 닫은 것 하나, 실패 로그면 빈 배열이다. 한 로그가 둘을 동시에 가질 수 없어 **배열 하나로 합쳐 보낸다** — 어느 쪽인지는 `source`가 말한다. 만든 순서로 온다.
- 지워진 태스크는 배열에서 **사라진다**. 완료 로그가 닫은 태스크는 되돌린 뒤에도 남지만, 다른 캡처가 그 태스크를 다시 닫으면 옛 로그의 배열이 빈다(연결이 덮이기 때문 — 아래 `rationale` 항목과 같은 설계, `03-Architecture.md` §설계 결정 24).
- `rationale`은 **완료 로그에서만 찬다.** 생성의 근거는 태스크마다 달라 태스크 쪽(`GET /api/v1/tasks`의 `rationale`)에 있다.
- `captureSummary`는 타임아웃(`AGT_TIMEOUT`)·LLM 오류 로그에서 `null`이다 — 요약이 모델 출력에서만 나오기 때문이다(설계 결정 17).
- `handledAt`은 사용자가 웹의 '확인 필요'(`DASH-11`)에서 그 로그를 **처리한 시각**이다 — [직접 처리]로 태스크를 저장했거나 [넘기기]를 눌렀을 때 찬다(`L-P1-11`). **로그는 지워지지 않는다**; 처리해도 이 목록에 그대로 남는다. '확인 필요'에 드는 것은 `capture_create`의 실패 중 `NO_TASK_TO_CREATE`·`AGENT_TIMEOUT`·`INTERNAL_ERROR`뿐이라 그 밖의 로그(성공·`DUPLICATE_TASK`·완료 실패)는 늘 `null`이다. 이 칸 하나만으로 "확인 필요에 남았나"를 판정할 수 없다 — 범위 조건은 서버에 한 벌만 있다(`API-5`). 처리 표시를 쓰는 HTTP 경로는 없다(웹의 Server Action만 쓴다). **추가된 칸이다**(2026-09-25) — 옛 클라이언트는 무시하면 된다.
- **LLM 계측(모델명·토큰·지연)은 싣지 않는다.** 원가 정보이고 앱에도 사용자에게도 쓸 데가 없다.
- 남의 로그는 배열에 들어오지 않는다. 토큰이 없으면 `401`.
- `revertable`은 **지금 이 로그에 되돌리기를 걸면 성공할지**를 DB가 판정한 값이다(`L-P1-02`). `NTF-5`와 히스토리 화면이 버튼 노출에 쓴다. **참고값이다** — 읽은 뒤 사용자가 그 태스크를 고치면 뒤집히고, 진짜 판정은 `POST …/revert`가 한 트랜잭션 안에서 다시 한다. `true`였는데 `409`가 오는 것은 정상이고, 그때는 `message`를 그대로 띄운다.

**`POST /api/v1/job-logs/:id/revert`** — 작업 로그 하나를 되돌린다(`HIST-3`, `HIST-4`).

**요청 본문이 없다.** 대상은 경로의 id가 전부 지정하고, 무엇을 되돌릴지는 로그의 `outcome`이 정한다 — 앱이 고르게 하면 앱과 서버의 판단이 갈라진다.

```jsonc
{
  "data": {
    "jobLogId": "uuid",
    "reverted": "created" | "completed",
    "taskIds": [ "uuid" ]
  }
}
```

- `reverted`는 로그의 `outcome`을 그대로 되비친다. `created`면 `taskIds`의 태스크가 **삭제**됐고, `completed`면 `todo`로 **되돌아갔다**.
- `taskIds`는 실제로 바뀐 태스크만 만든 순서로 담는다. 성공 응답에서 **빈 배열일 수 없다** — 0건이면 `409`다.
- **멱등하지 않다.** 두 번째 호출은 `409`이고 그것이 계약이다.
- **생성 되돌리기는 all-or-nothing이다.** 한 로그가 태스크 N개를 만들 수 있는데(`AGT-1`), 하나라도 생성 이후 변경됐으면 **한 건도 지우지 않고** 거절한다. "일부는 지우고 일부는 남겼다"는 사용자에게 설명할 수 없다.
- 태스크를 지우면 태그 연결(`task_tags`)이 함께 사라진다. 태그 자체는 남는다.
- **완료 되돌리기는 `completed_by_job_log_id` 연결을 남긴다.** 되돌린 태스크는 여전히 그 로그의 `tasks[]`에 실려, 무엇을 되돌렸는지가 히스토리에서 보인다.

되돌릴 수 없으면 `409` + `REVERT_NOT_POSSIBLE`. `code`는 하나뿐이고 사유는 `message`로 갈린다 — 앱은 분기하지 말고 문장을 그대로 띄운다.

| 사유 | 언제 | `message` |
|---|---|---|
| 태스크가 변경됨 | 생성 로그의 태스크 중 하나라도 생성 이후 바뀜 (`HIST-4`) | 생성 이후 태스크가 변경되어 되돌릴 수 없습니다. |
| 되돌릴 태스크 없음 | 태스크가 지워졌거나, 이미 되돌렸거나, 다른 캡처가 그 태스크를 다시 닫아 연결이 덮임 | 되돌릴 태스크가 남아 있지 않습니다. |
| 이미 미완료 | 완료 로그인데 그 태스크가 이미 `todo` (`HIST-4`) | 이미 되돌린 작업입니다. |
| 되돌릴 내용 없음 | `outcome`이 `failed` — 쓴 것이 없다 | 되돌릴 내용이 없는 기록입니다. |

- **"삭제되었습니다"라고 쓰지 않는 것이 의도다.** 태스크가 지워진 경우와 연결이 덮인 경우가 서버에서 같은 관측(가리키는 행 0건)으로 수렴해 **구분할 수 없다.** 구분할 수 없는 것을 구분한다고 말하지 않는다 — `HIST-4`의 "사용자가 그 사이 수정함"에서 '사용자가'를 뺀 것과 같은 규율이다.
- 없는 로그·남의 로그·`:id`가 UUID 꼴이 아닌 경우는 **본문까지 동일한** `404` + `JOB_LOG_NOT_FOUND`다.
- 토큰이 없으면 `401`.

> ⚠️ **알려진 한계** — 완료를 되돌린 뒤 사용자가 그 태스크를 **직접 다시 완료**하면 연결이 남아 있어 같은 로그의 되돌리기가 **다시 가능해진다.** 그 되돌리기는 사용자의 수동 완료를 `todo`로 만든다. 연결을 지우면 히스토리에서 '관련 태스크'가 영구히 비므로 남기는 쪽을 택했다(2026-09-24 결정). 상태 전환은 되돌릴 수 있어 생성 되돌리기의 삭제와 위험이 다르다.

**`POST /api/v1/tags/merge`** — 태그 둘을 하나로 합친다(`DASH-6`).

```jsonc
// 요청
{ "sourceId": "uuid", "targetId": "uuid" }

// 응답 — 남은 태그(target) 한 건
{ "data": { "id": "uuid", "name": "업무", "createdAt": "2026-09-20T05:30:00Z" } }
```

- `source`의 태스크가 전부 `target`으로 옮겨지고 `source`는 **사라진다**. **태스크는 한 건도 사라지지 않는다** — 옮기기와 지우기가 DB 함수 `merge_tags` 안에서 한 트랜잭션이다.
- 둘 다 달려 있던 태스크에는 `target`이 **한 번만** 남는다(`task_tags`의 PK가 걸러 준다).
- 응답의 `id`·`createdAt`은 **병합 전 `target`과 같다.** 병합은 그 행을 만들지도 고치지도 않는다.
- **멱등하지 않다.** 두 번째 호출은 출발 태그가 없어 `404`이고 그것이 계약이다.
- **'미분류'는 `source`로 쓸 수 없다** — `409 TAG_PROTECTED`(`AGT-5`의 전제가 사라진다). **`target`으로는 허용한다** — 태그가 하나도 없어지지 않고, "잘못 만든 태그를 미분류로 되돌린다"는 정상 동선이다. 보호가 대칭이 아닌 것이 의도다.
- 둘 중 하나라도 없거나 남의 태그면 `404 TAG_NOT_FOUND`다. **남의 '미분류'도 `TAG_PROTECTED`가 아니라 `404`** — 보호 여부는 출발 태그가 **보일 때만** 답한다. 아니면 그 id가 실재한다는 것을 흘린다.
- 두 id가 같거나, 빠졌거나, UUID 꼴이 아니면 `400 VALIDATION_FAILED`다. **경로의 `:id`와 달리 404로 합류시키지 않는다** — 여기는 본문이라 "형식이 틀렸다"가 그대로 `400`이다.
- 토큰이 없으면 `401`.

> 📱 앱이 태그 목록을 캐시한다면 병합 뒤 **사라진 id가 손에 남을 수 있다.** 태스크의 `tags`와 어긋나면 목록을 다시 받는다.

### 이벤트 채널 (`API-7`) — P2

메일 소스 결과는 앱 요청 없이 서버에서 생긴다. 폴링과 실시간 구독 중 하나를 P2 착수 시 정한다.

> 대시보드의 Realtime 구독(`L-P0-13`)은 **이것이 아니다.** 저쪽은 브라우저가 자기 행을 RLS 아래에서 직접 구독하는 것이고(`DASH-5`), 여기는 **앱**에 서버발 결과를 알리는 채널이다 — 앱은 Supabase를 직접 부르지 않는다(`API-1`).

## 변경 규칙

- **깨는 변경**(필드 제거·의미 변경·경로 변경)은 앱과 합의 후 `/api/v2`로 낸다.
