# 07 — 프롬프트 작성 원칙

> **에이전트 프롬프트(`AGT-*`)를 쓸 때 여는 문서다.** 원칙 → 이 프로젝트 적용 → 프롬프트 골격 순으로 읽는다.

>
> 원칙은 프로바이더 중립이다. 이 프로젝트의 런타임 LLM은 **OpenAI (GPT)** 이지만, 아래 원칙은 구조적인 것이라 그대로 적용된다. 프로바이더별 파라미터(모델 ID, 구조화 출력 스펙 등)는 [`03-Architecture.md`](03-Architecture.md) §설계 결정 4에서 확인한다.

## 황금률

> **맥락을 거의 모르는 동료에게 프롬프트를 보여주고 따라 해 보라고 했을 때 그가 헷갈린다면, 모델도 헷갈린다.**

가장 좋은 프롬프트는 가장 길거나 복잡한 것이 아니라, **필요한 최소 구조로 목표를 안정적으로 달성하는 것**이다.

## A. 기본 원칙

### A1. 명확하고 직접적으로

모델을 "똑똑하지만 우리 관행을 전혀 모르는 신입"으로 대한다. 원하는 출력 형식과 제약을 구체적으로 말한다. 순서나 빠짐없음이 중요하면 번호 목록으로 준다.

- ❌ `분석 대시보드를 만들어줘`
- ✅ `분석 대시보드를 만들어줘. 관련 기능과 상호작용을 가능한 한 많이 넣고, 기본 수준을 넘어 완결된 구현을 해줘.`

### A2. 지시에 **이유**를 붙인다

왜 그래야 하는지를 알려주면 모델이 일반화한다. 규칙만 주면 그 규칙이 적용되지 않는 경우에 무너진다.

- ❌ `절대 말줄임표를 쓰지 마`
- ✅ `응답은 TTS 엔진이 읽는다. 말줄임표는 발음할 수 없으니 쓰지 마.`

### A3. 예시로 보여준다 (few-shot)

출력 형식·톤·구조를 잡는 가장 확실한 수단이다. **3~5개**가 적당하다.

- **관련성** — 실제 사용 사례를 그대로 닮게.
- **다양성** — 엣지 케이스를 덮고, 모델이 의도치 않은 패턴을 집어가지 않을 만큼 서로 다르게.
- **구조** — `<example>` 태그로 감싸 지시문과 구분한다(여러 개면 `<examples>`).

### A4. XML 태그로 구조화

지시·맥락·예시·가변 입력이 한 프롬프트에 섞이면 모델이 경계를 헷갈린다. 종류별로 태그를 씌운다(`<instructions>`, `<context>`, `<input>`). 태그 이름은 프롬프트 전반에서 **일관되게**, 계층이 있으면 중첩한다.

### A5. 역할을 준다

시스템 프롬프트 한 문장이 도메인 과제 성능을 눈에 띄게 올린다. `당신은 ~ 전문가다` 한 줄로 충분할 때가 많다.

### A6. 긴 맥락은 **자료를 위, 질의를 아래**

20k 토큰 이상의 입력에서:
- 긴 문서·데이터를 프롬프트 **맨 위**에, 질의와 지시를 **맨 아래**에 둔다. 복잡한 다중 문서 입력에서 응답 품질이 최대 30%까지 올라간다.
- 문서마다 `<document>` / `<source>` / `<document_content>`로 감싼다.
- **인용을 먼저 뽑게 한다** — "관련 대목을 `<quotes>`에 먼저 인용한 뒤, 그것을 근거로 답하라." 모델이 관련 없는 부분을 흘려보내게 된다.

### A7. "하지 마" 대신 "하라"

- ❌ `마크다운을 쓰지 마`
- ✅ `매끄럽게 이어지는 산문 문단으로 써라`

형식을 강제하려면 XML 태그로 출력 위치를 지정하거나, **프롬프트 자체의 문체를 원하는 출력 문체에 맞춘다**(프롬프트에서 마크다운을 빼면 출력의 마크다운도 준다).

### A8. 모를 때는 모른다고 말하게 허락한다

추측 대신 한계를 인정할 **명시적 허가**를 주면 환각이 줄어든다.

- ✅ `근거가 부족하면 추측하지 말고 비워 두고, 왜 비웠는지 적어라.`

### A9. 스스로 검산하게 한다

`끝내기 전에 [기준]에 비추어 답을 검증하라.` 코딩·수치 과제에서 특히 잘 듣는다.
단, **과잉 검증도 비용이다.** 최신 모델일수록 알아서 검증하므로, 옛 모델용 검증 지시를 그대로 옮기면 토큰과 지연만 늘어난다.

### A10. 단계별 추론을 요청한다

복잡한 다단계 과제에서는 `단계적으로 생각하라`가 정확도를 크게 올린다. 추론과 최종 출력을 `<thinking>` / `<answer>` 태그로 갈라 두면 파싱도 쉬워진다.
일반 지시("충분히 생각하라")가 사람이 손으로 쓴 단계 계획보다 나은 경우가 많다 — **과정을 규정하기보다 목표를 규정한다.**

### A11. 복잡하면 체인으로 나눈다

가장 흔한 패턴은 **자기 교정**이다: 초안 생성 → 기준에 비추어 검토 → 검토를 반영해 수정. 각 단계를 별도 호출로 두면 중간 산출물을 로깅·평가·분기할 수 있다. [`06-Loop-Engineering.md`](06-Loop-Engineering.md)의 L1/L2와 같은 모양이다.

### A12. 과잉 엔지니어링을 막는다

모델은 요청하지 않은 파일·추상화·유연성을 만들어내는 경향이 있다. 억제하려면 명시한다: 범위 밖 개선 금지 / 건드리지 않은 코드에 주석 추가 금지 / 일어날 수 없는 상황에 방어 코드 금지 / 일회성 작업에 헬퍼 만들지 말기. **필요한 최소 복잡도가 정답이다.**

### A13. 테스트 통과에만 맞추지 않게 한다

`테스트는 정답을 정의하는 것이 아니라 정확성을 확인하는 것이다. 모든 유효한 입력에 대해 동작하는 일반해를 구현하라. 값을 하드코딩하지 마라. 과제가 불합리하거나 테스트가 틀렸다면 우회하지 말고 알려라.`

### A14. 행동 여부를 명시한다

"~를 제안해 줄래?"라고 물으면 제안만 하고 끝낸다. 실행을 원하면 **실행형으로 쓴다**("이 함수의 성능을 개선해라"). 반대로 조사만 원하면 그것도 명시한다.

### A15. 독립적인 도구 호출은 병렬로

서로 의존하지 않는 호출은 한 번에 보낸다. 단, 앞선 호출 결과가 뒤 호출의 인자를 정한다면 순차로 한다. **자리표시자를 쓰거나 빠진 인자를 추측하지 않는다.**

### A16. 과잉 지시를 경계한다

최신 모델은 `반드시`, `CRITICAL` 같은 강한 표현에 과민하게 반응해 **필요 없을 때도 도구를 호출**한다. `~할 때 이 도구를 써라` 정도의 평범한 문장이면 충분하다. 옛 모델용으로 세게 써 둔 지시는 모델을 바꿀 때 오히려 덜어내야 한다.

## B. 이 프로젝트에 적용할 때

제품의 대원칙([`00-Product.md`](00-Product.md) §5 결정 기록)을 프롬프트 문장으로 옮기면 이렇게 된다.

| 제품 결정 | 프롬프트에 쓸 문장 | 관련 원칙 |
|---|---|---|
| 에이전트는 되묻지 않는다 (결정 2) | `사용자에게 질문하지 마라. 후보가 여럿이면 가장 그럴듯한 하나를 골라 확정하라.` | A1, A14 |
| 신뢰도 지표를 두지 않는다 (결정 2) | 신뢰도 필드를 **스키마에 넣지 않는다.** 없는 칸은 채워지지 않는다 | A1 |
| 추측하지 않는다 (`AGT-4`) | `마감일이 캡처에 드러나지 않으면 추측하지 말고 null로 두어라.` | A8 |
| 근거 한 문장 (`AGT-1`) | `왜 그렇게 판단했는지 캡처에서 본 것을 근거로 한 문장 적어라.` | A6 인용-먼저 |
| 기존 태그 우선 (`AGT-5`) | 사용자의 **기존 태그 목록을 입력에 넣고**, `확실히 새로운 일일 때만 새 태그를 만들어라. 애매하면 '미분류'.` | A1, A2 |
| 10초 예산 (`AGT-9`) | 프롬프트를 짧게 유지하고 추론 깊이를 과하게 요구하지 않는다 | A9 과잉 검증 경계 |
| 캡처 무저장 (`AGT-10`) | 이미지는 요청 한 번에만 실린다. **대화를 이어가는 구조를 쓰지 않는다** | — |

### 반드시 구조화 출력을 쓴다

`AGT-1`의 결과는 그대로 DB에 들어간다. 자유 텍스트를 파싱하지 않고 **스키마를 강제**한다. 스키마에 없는 필드는 모델이 만들어낼 수 없으므로, 스키마 자체가 결정 기록을 강제하는 장치가 된다(신뢰도 필드 부재가 대표적).

### 평가는 루프로 돌린다

프롬프트는 한 번 쓰고 끝나지 않는다. 대표 캡처 세트를 고정해 두고, 프롬프트를 고칠 때마다 같은 세트로 돌려 비교한다. [`06-Loop-Engineering.md`](06-Loop-Engineering.md)의 L4(개선 루프)가 이것이다.

## C. 프롬프트 골격

`AGT-1`~`AGT-5`(생성 캡처) 프롬프트의 뼈대. **실제 문구는 [`lib/agent/create-prompt.ts`](../lib/agent/create-prompt.ts)** 이고, 고칠 때마다 `npm run grade`로 평가 세트를 다시 돌린다. 아래 골격과 달라진 점 셋:

- `captured_at`을 ISO가 아니라 **현지 표기 + 요일**(`2026-09-19 (토) 21:00`)로 준다. 요일은 서버가 계산한다 — '다음 주 월요일' 환산을 모델의 요일 계산에 맡기지 않는다.
- 마감은 `dueAt` 하나가 아니라 **`dueDate` + `dueTime`** 으로 받고, 시간대 변환은 서버가 한다([`03-Architecture.md`](03-Architecture.md) §설계 결정 14).
- `quotes`에 **화자(`speaker`)** 를 붙인다. 메신저에서 사용자와 상대를 뒤바꾸는 오판을 지시문으로는 못 막았고, 칸으로 강제하자 잡혔다(같은 문서 §설계 결정 15).

```xml
<!-- system -->
당신은 사용자의 화면 캡처에서 업무 태스크를 읽어내는 분석기다.        <!-- A5 역할 -->
사용자에게 질문하지 않는다. 판단이 필요하면 가장 그럴듯한 하나를 확정한다.  <!-- A14, 결정 2 -->

<!-- user : 긴 자료가 위, 질의가 아래 (A6) -->
<context>
  <captured_at>2026-09-20T14:30:00+09:00</captured_at>
  <timezone>Asia/Seoul</timezone>
  <existing_tags>마케팅, A 캠페인, 미분류</existing_tags>   <!-- AGT-5 -->
</context>

<image>…</image>

<examples>                                                <!-- A3: 3~5개 -->
  <example>…채팅창에 할 일이 하나 → 태스크 1개…</example>
  <example>…회의록에 할 일이 셋 → 태스크 3개…</example>
  <example>…업무 맥락만 있고 할 일 없음 → 요약 제목 1개 (AGT-2)…</example>
  <example>…업무와 무관 → 빈 배열 (AGT-3)…</example>
</examples>

<instructions>
1. 캡처에서 근거가 되는 문구를 먼저 <quotes>에 인용하라.      <!-- A6 인용-먼저 -->
2. 인용을 근거로 태스크를 식별하라. 여러 개면 각각 만들어라.    <!-- AGT-1 -->
3. '내일', '금요일까지'는 captured_at과 timezone 기준 절대 날짜로 바꿔라.
   드러나지 않으면 추측하지 말고 null로 두어라.                <!-- AGT-4, A8 -->
4. 태그는 existing_tags에서 먼저 고르고, 확실히 새로운 일일 때만
   새로 만들어라. 애매하면 '미분류'.                          <!-- AGT-5 -->
5. 각 태스크에 왜 그렇게 판단했는지 한 문장 근거를 붙여라.      <!-- AGT-1 -->
</instructions>
```

출력은 자유 텍스트가 아니라 **구조화 출력 스키마**로 받는다: `{ quotes: [{ speaker, text }], summary, tasks: [{ title, description|null, dueDate|null, dueTime|null, tags[], rationale }] }`. `summary`는 작업 로그의 한 줄 요약(`AGT-8`)이다. `AGT-3`이면 `tasks`는 빈 배열이다.

**완료 캡처(`AGT-6`·`AGT-7`)는 같은 골격이다 — 실제 문구는 [`lib/agent/complete-prompt.ts`](../lib/agent/complete-prompt.ts)**, 평가는 `npm run grade -- complete`. 다른 점: `<context>`에 태그 목록 대신 **미완료 태스크를 번호 목록**(`<open_tasks>`)으로 싣고, 출력은 `{ quotes, summary, rationale, taskKey: 번호|null }`이다. `taskKey`는 요청마다 그 번호들의 enum으로 만들어져 목록 밖을 고를 수 없다([`03-Architecture.md`](03-Architecture.md) §설계 결정 16). 지시의 중심은 **"남이 끝낸 일은 사용자의 완료가 아니다"** 와 **"억지로 고르는 것이 아무것도 안 바꾸는 것보다 해롭다"**(A8·A14) 두 가지다.
