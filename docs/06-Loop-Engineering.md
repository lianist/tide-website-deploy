# 06 — Loop Engineering (개발 방법론)

> **이 프로젝트를 어떻게 굴리는가.** 진행 상황 자체는 [`ROADMAP.md`](ROADMAP.md)가 유일한 소스다.
> 리서치 출처: [LangChain — The Art of Loop Engineering](https://www.langchain.com/blog/the-art-of-loop-engineering) · [MindStudio — What Is Loop Engineering?](https://www.mindstudio.ai/blog/what-is-loop-engineering-ai-coding-agents)

## 왜 루프인가

코딩 에이전트의 품질 차이는 베이스 모델이 아니라 **루프 설계**에서 나온다. 루프란 *추론 → 행동 → 결과 관찰 → 반복*을 **측정 가능한 목표를 만족하거나 측정 가능한 검사에 실패할 때까지** 도는 구조다.

여기서 중요한 낱말은 **측정 가능**이다. "앱이 더 나아 보인다"는 종료 조건이 될 수 없다. "`npm run typecheck`가 0을 반환한다"는 될 수 있다. 목표가 측정 불가능하면 루프는 멈추지 않거나, 아무 때나 멈춘다.

## 4계층 루프

| 계층 | 이름 | 무엇이 도는가 | 언제 멈추는가 |
|---|---|---|---|
| **L1** | 구현 루프 | 코드 작성 → 실행 → 에러 관찰 → 수정 | 루프 단위의 완료 조건이 전부 충족 |
| **L2** | 검증 루프 | 게이트 G1~G5 실행 → 실패 피드백 → L1로 반송 | 게이트 전부 통과 |
| **L3** | 과제 루프 | `ROADMAP.md`의 루프 단위를 순서대로 소진 | 해당 우선순위의 모든 루프가 `[x]` |
| **L4** | 개선 루프 | 세션 회고 → 반복된 실패 패턴을 규칙으로 승격 | 세션 종료 시 1회 |

**상위 계층은 하위 계층을 더 낫게 만든다.** L4가 L2의 게이트를 손보면 이후 모든 L1이 덜 실패한다. 회고가 문서로 돌아가지 않으면 그건 나쁜 루프다.

## 루프 단위 (Loop Unit)

개발 과제를 쪼개는 최소 단위다. **한 루프는 혼자서 검증될 수 있어야 한다.** 다른 루프가 끝나야만 확인 가능한 것은 루프가 아니라 루프 두 개다.

```markdown
### L-P0-07 · LLM 어댑터 choke point
- **커버**: (기반) AGT-1~AGT-9
- **목표**: 모든 LLM 호출이 단일 모듈을 통과하고 토큰·지연·모델이 DB에 계측된다
- **완료 조건**
  - [ ] `lib/llm/` 밖에서 openai SDK를 import 하면 `npm run lint`가 실패한다
  - [ ] 호출 1건 후 `job_logs`에 model·prompt_tokens·completion_tokens·latency_ms가 기록된다
- **검증**: `npm run test -- llm-adapter` · 저비용 모델로 실제 호출 1회
- **상한**: 3회 실패하면 멈추고 사람에게 보고
```

필수 5항목: **커버 · 목표 · 완료 조건 · 검증 · 상한.** 하나라도 비면 그 루프는 아직 착수 가능하지 않다.

### 완료 조건 쓰는 법

- 명령 한 줄로 확인되면 가장 좋다 (`npm run build`).
- UI는 Playwright 시나리오 이름으로 쓴다 ("마감 지난 태스크에 `.overdue` 클래스가 붙는다").
- "잘 동작한다", "깔끔하다" 같은 말은 완료 조건이 아니다.

## 게이트 (모든 루프 공통)

| 게이트 | 검사 | 통과 기준 |
|---|---|---|
| **G1 정적** | `npm run lint` · `npm run typecheck` | 경고 0, 에러 0 |
| **G2 빌드** | `npm run build` | 성공 |
| **G3 기능** | 루프의 자동 테스트 (API 요청 테스트 / Playwright) | 전부 통과 |
| **G4 계약** | API가 바뀌었다면 [`04-API-Contract.md`](04-API-Contract.md) 갱신 | 같은 커밋에 포함 |
| **G5 기록** | [`ROADMAP.md`](ROADMAP.md) 상태 갱신 + 비자명한 결정을 해당 문서에 반영 | 같은 커밋에 포함 |

**게이트를 통과하지 못한 루프는 완료가 아니다.** 다음 루프로 넘어가지 않는다.

## 실패 처리

- **같은 접근을 반복하지 않는다.** 같은 수정을 두 번째 시도할 거라면, 그건 학습이 아니라 자원 낭비다. 가설을 바꾼다.
- 실패 피드백은 **구조화해서** L1로 돌린다: 원본 코드 + 에러 전문 + 지금까지 시도한 것.
- **상한 3회.** 세 번째 실패에서 멈추고 사람에게 보고한다. 무엇을 시도했고 왜 실패했는지를 함께 낸다.
- 되돌릴 수 없는 작업(마이그레이션 원격 push, 배포, force push)은 상한과 무관하게 **사전 확인**을 받는다.

## 우선순위 격리

**P0의 모든 루프가 `[x]`가 되기 전에는 P1 루프에 착수하지 않는다.** P1 → P2 → P3도 같다.

- ROADMAP의 각 우선순위 블록 끝에 **우선순위 게이트** 항목을 둔다. 물리적으로 체크해야 다음 블록이 열린다.
- P1 요구사항이 눈에 띄어도 "간 김에" 하지 않는다. P0가 흔들린다.
- 예외는 하나뿐이다: **P0를 완성하기 위해 반드시 필요한 상위 우선순위 항목.** 이때는 그 이유를 ROADMAP에 한 줄 적고 해당 루프를 P0로 끌어내린다.

## 인간 개입 지점

자동화가 인간 판단을 완전히 배제하면 나쁜 루프다. 대신 **민감한 지점에만** 배치한다.

| 개입 | 언제 |
|---|---|
| **사전 확인** | 되돌릴 수 없는 작업, 비용이 큰 LLM 실험, 요구사항 자체가 모호할 때 |
| **중단 보고** | 같은 루프에서 3회 실패했을 때 |
| **회고 승인** | L4가 규칙을 바꾸자고 제안할 때 |

반대로 **사소한 건마다 멈추지 않는다.** 파일 하나 고칠 때마다 묻는 루프는 루프가 아니다.

## 세션 회고 (L4)

세션을 닫기 전에 세 가지를 확인한다.

1. **반복된 실패가 있었나?** → 게이트나 `CLAUDE.md` 규칙으로 승격한다.
2. **문서에 없어서 다시 알아낸 것이 있었나?** → 해당 문서에 적는다.
3. **ROADMAP이 실제 상태와 맞나?** → 맞춘다.

## 제품도 같은 모양이다

Dochi 제품 자체가 루프다. 그리고 그 구조는 우리 개발 방식과 같다.

| | 개발 | 제품 |
|---|---|---|
| **L1** | 에이전트가 코드를 쓰고 테스트를 돌린다 | 에이전트가 **되묻지 않고** 태스크를 만들거나 완료한다 (`AGT-6`, Non-goals) |
| **L2** | 게이트가 걸러낸다 | 사용자가 대시보드·히스토리·[되돌리기]로 **사후 교정**한다 (결정 기록 3) |

둘 다 **"먼저 처리하고 나중에 바로잡는다"** 는 같은 원칙 위에 서 있다. 승인 팝업을 버린 이유([`00-Product.md`](00-Product.md) §3 폐기된 가정)와, 파일 하나 고칠 때마다 묻지 않는 이유는 같다 — **개입 비용이 오류 비용보다 비싸기 때문이다.**

에이전트 프롬프트를 쓸 때 이 원칙을 어떻게 문장으로 옮기는지는 [`07-Prompt-Principles.md`](07-Prompt-Principles.md)에 있다.
